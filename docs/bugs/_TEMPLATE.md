# [BUG] <一句话标题：现象概述>

## 元信息

| 项 | 值 |
| --- | --- |
| 状态 | 已定位 / 修复中 / 已修复 |
| 仓库/模块 | 桥（src/core.ts…）/ App（BridgeClient.kt…） |
| 发现方式 | 真机验收 / 自测 / 用户报告 / 日志告警 |
| 日期 | YYYY-MM-DD |
| 相关 commit | <修复提交哈希> |
| 关联文档 | 其它 bug 文档 / 设计文档链接 |

## 背景

- 相关功能/机制的设计意图与历史（含此前为修别的 bug 打过的补丁——很多新 bug 是旧补丁引入的）。

## 现象

- 用户可感知的现象，越具体越好（时间、路径、复现步骤、出现频率）。
- 附真机/日志证据（UI dump 文本、logcat 摘录、服务端日志 seq/时间戳）。

## 排查过程

- 按时间线记录：观察到什么 → 排除了什么假设 → 用什么证据锁定。
- 记录排查受限点（如日志缓冲被系统滚动覆盖导致关键窗口取证失败——这是华为真机的已知限制）。

## 根因分析（必须挖到深层，不允许停留在表面现象）

- 表面原因：直接触发 bug 的代码路径（哪个标志位/定时器/竞态）。
- **深层根因**：为什么这个设计会允许该竞态存在——通常是「状态归属模型」问题
  （多个异步时间线写同一状态而无单一事实源 / 标志位靠事件对称置清而非从真实状态推导 /
  旧补丁与原始设计目标冲突）。给出可推广的教训。

## 解法

- 方案说明（为什么这样修，而不是别的）。
- **核心 Code Diff**（关键几行的 before/after）。
- 提交哈希：<hash>（工作树分支 / main）。
- 回归测试：新增了哪些断言/单测。

## 后续改进计划

- 待办：回填 commit、加固测试、上位的系统性改进（如状态机重构）等。
- 教训推广：同类模式在其它地方的排查清单。
