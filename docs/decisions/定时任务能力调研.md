## 一、需求背景

- **为什么做**：用户把「定时任务 / Cron」视为其 agentic workflow 的**核心组成部分**，明确要求该能力必须支持（参照 OpenClaw 已有的 Cron 能力）。现有体系里唯一的「定时」先例是每日早报——用 macOS `launchd` 在 08:12 拉起 `morning-report` skill（**外部调度**，不是 DSH 原生），并非「定时触发 DSH 会话」。
- **要回答的问题**：DSH 到底有没有原生定时/Cron 能力？没有的话，如何在这个自托管服务端（Mac）＋ 桥插件（Node/TS 常驻）＋ 移动端（KMP Compose，服务端投影为准）的体系里实施等价能力？
- **边界**：本阶段**只调研论证，不实施代码**；产出论证文档供用户拍板。不 commit。

---

## 二、核心需求点拆解

1. **定时触发**：能按 Cron 表达式（"每天 08:00"、"每周一 09:00"）或相对延时触发一次「agent 任务」。
2. **持久化与重启存活**：任务表不因进程重启/热重载丢失；重启后自动重新挂起调度、不丢任务。
3. **错过补跑**：进程在调度点不可用（崩溃/重启/停机）时，恢复后能识别并（按策略）补跑错过的触发。
4. **时区/夏令时**：按 IANA 时区解释 Cron，正确处理夏令时切换（缺口/重叠）。
5. **触发 agent 会话**：调度到时能把一段任务 prompt 注入到目标 agent 会话并驱动其执行（不是只打印到日志）。
6. **移动端联动**：定时任务的结果能推送到手机（复用已建的通知补投递体系），任务可被移动端查看/管理。
7. **可管理性**：任务的创建/查询/删除/立即运行，具备服务端投影、单向数据流。

## 三、核心指标拆解

| 指标 | 目标口径 | 测量方法 |
| --- | --- | --- |
| 触发准点率 | 与 Cron 计划点偏差 < 数秒（进程存活时） | 日志时间戳对比 |
| 重启存活 | 进程重启后任务 0 丢失、自动重 arm | 重启后 `/remote/health` 校验任务表 |
| 错过补跑 | 恢复后 N 分钟内识别并补跑（策略可配） | last-run 指纹 vs 计划点 |
| 时区正确性 | DST 切换日按 IANA 规则正确触发 | croner 库 + 单测 |
| 移动端送达 | 任务结果在 100~300ms 内推到手机（铁律 7） | WS 下行链路计时 |

## 五、技术方案设计

### 5.1 DSH 现状盘查（事实依据）

> 结论先行：**DSH 没有原生 Cron（无 Cron 表达式、无进程级调度服务）**，但存在两个相关能力：① 一个已发布但**默认未接入**的 `dsh-schedule` 插件（会话内「提醒」，after/at/every，非 Cron）；② 一个已接入的 `cordis-plugin-timer` 定时器服务（插件可 `ctx.interval` 长驻）。分述如下。

**（1）`@deepseek-ai/dsh-schedule` —— 会话内持久提醒，非 Cron，默认未启用**

- DSH CLI 版本 `0.1.1-rc.2`（`@deepseek-ai/dsh/package.json:4`）。
- `dsh-schedule` 作为 CLI 的**直接依赖**存在（`package.json:71`），但**未被任何默认 bundle patch 接入**：
  - `dsh-base/cordis.patch.yml`、`dsh-web-app/cordis.patch.yml`、`dsh-headless/cordis.patch.yml` 三个 patch 里**均无 `schedule` 行**（grep 全量确认，仅 base 里 `timer` 行与 `scheduledDelayMillis` 与调度无关）。
  - 全 node_modules 里 `grep -rln "dsh-schedule"` 只命中该包自身，**没有任何其它包引用它**。
  - ⇒ 当前用户 `web` profile（bundles = `dsh-base` + `dsh-web-app` + agent-teams + bridge + vision-toolkit）**没有加载 Schedule**。
- 它提供 3 个「会话范围」工具：`schedule_create` / `schedule_list` / `schedule_delete`（`dsh-schedule/lib/index.js:1171/1252/1274`）。
- 支持的规则（`README.zh.md:5,21-25`，`index.js:1179-1207`）：
  - `after_seconds`：正安全整数延时；
  - `at`：严格 RFC 3339 绝对时刻（带 `Z` 或偏移），或 `{ date, time, time_zone }`（本地形式必须显式 `UTC` 或 IANA Area/Location）；
  - `every_seconds`：固定速率间隔，**下限 300s（5 分钟）**，与创建锚点对齐。
  - **明确无 Cron**：README 原文（中英一致）「日历表达式或 Cron 表达式不是协议的一部分（calendar or Cron expressions are not part of the protocol）」（`README.zh.md:114` / `README.md:114`）。
- 持久化：提醒状态**归会话事件日志所有**（`schedule/change` 的 create/delete/dispatch 联合，version 1），经 `ctx.sessions.flush(session)` 与 `sessionPersistence` 持久化（`README.zh.md:5,15-19`；`types.d.ts:172-179`）。`inject = ["agents","sessions","tools","sessionPersistence"]`（`index.js:1345-1350`）。
- 触发路径：`ScheduleRuntime` 监听 `agent/created` 为每个 live 根 agent 挂一个运行时；到期时 `runMaintenance()` → 构造 framing → `this.agent.followup(message)` 排队一个普通后续轮次（`index.js:813,825-835`；framing 格式见 `README.zh.md:69-99`）。
- **关键限制（直接影响本需求）**：
  - **仅限会话本地交付（session-local delivery）**：提醒只在**原会话 live 时**才能准时运行；冷会话收不到任何外部通知，只有恢复后才处理 overdue 记录（`README.zh.md:111`）。
  - **只追赶最新一次**：逾期 Every 记录只贡献最新一个发生时点，从不回放错过的积压（`README.zh.md:115`）。
  - 活动驱动的重试（无私有重试 timer）、固定间隔非日历规则、崩溃重复窗口（`README.zh.md:112,114,116`）。

**（2）`@deepseek-ai/cordis-plugin-timer` —— 插件可用的 disposal-aware 定时器，已接入**

- 作为 CLI 依赖（`package.json:28`），且**已接入 base bundle**：`dsh-base/cordis.patch.yml:16-17` 的 `id: timer` 行。
- API（`cordis-plugin-timer/src/index.ts:24-145`）：`ctx.timeout(cb,delay)` / `ctx.timeout(delay)`（Promise）、`ctx.interval(cb,delay)` / `ctx.interval(delay)`（异步迭代器）、`ctx.throttle` / `ctx.debounce`；`ctx.setTimeout`/`ctx.setInterval` 为 deprecated 别名。
- 关键特性：**定时器句柄注册在当前 fiber 上，插件 dispose 时自动 clear**（README + `src/index.ts:35-42,63-66`）。
- ⇒ 结论：**插件完全可以在进程内 `ctx.interval`/`setInterval` 长驻**，且框架已为其做了生命周期（dispose 自动清理）保障。

**（3）插件进程生命周期 / 热重载对定时器的影响（事实）**

- 桥插件以 Cordis bundle 方式常驻（`dsh-remote-control-bridge/src/index.ts:4-13,22-23`），`inject = ['webServer','sessions','agents','workspaceRegistry','sessionTitle','sessionPersistence','tools']`。
- 桥已在进程内大量使用**裸 `setInterval`/`setTimeout`**（`core.ts:156,811,1258,1323,2386` 等），并在 `ctx.effect(() => () => {...})` 的 dispose 路径里**逐一 `clearInterval`/`clearTimeout`**（`core.ts:2806-2832`）。
- 桥的**热重载**机制（`reloader.ts`）：`/remote/reload` 或 `fs.watch` 触发时，先 `dispose` 旧 core fiber（触发上面那套清理 → **清掉旧实例的全部定时器**），再从版本化 staging 目录 `import` 新 core 重新 `apply`（`reloader.ts:272-334`）。
- ⇒ 结论：**in-process 定时器在热重载 / 进程重启时必然丢失**；要可靠，必须「任务表持久化到文件 + boot/热重载后重新 arm + last-run 指纹补跑」。桥已有此模式先例（见下）。

**（4）桥插件现有「文件 KV 持久化」与「注入消息」先例（事实）**

- 文件 KV 持久化（可直接照搬的范式）：
  - `work.ts`：`$DSH_HOME/remote-control-work.json`（0600），重启后续跑/待办恢复（`work.ts:1-11,82-112`）。
  - `deliveries.ts`：`$DSH_HOME/remote-control-deliveries.json`（0600），结果交付通知台账，重连补发、上限淘汰（`deliveries.ts:1-10,53-58`）。
- 注入 agent 会话的通道（方案 A 的触发点）：
  - `core.ts:842-867`：运行中 `agent.inject(message)`（下一步推理立即看到，不 steer 打断）；空闲 `agent.followup(message)` 唤醒。
  - `createUserMessage` 带 `source: { kind: 'plugin', plugin: 'dsh-remote-control-bridge', form: 'notice', ... }`（`core.ts:852-860`）。
  - Agent 注入语义（官方类型）：`agent.followup(msg)` = 排队普通后续轮次并唤醒；`agent.inject(msg)` = 下一 pre-step 注入上下文不唤醒；`agent.steer(msg)` = 最近一步 steering（`dsh-agent/lib/types/runtime-types.d.ts:109-132`）。
- 会话读取：`ctx.sessionPersistence.readFrom(SessionId(sid), 0)`（`core.ts:1068-1069`）。
- **桥没有「注入消息」的 HTTP 端点**（现有路由：`/remote/ws /ping /health /work /sessions /pair-info /pair /devices /connected /debug/* /logs /phone-logs`，见 `core.ts:2435-2768`）——手机发消息走 WS，注入只在进程内 `agent.inject/followup`。⇒ 方案 B（外部调度调桥注入）**需新增一个注入端点**。
- 桥当前**没有 cron 库依赖**（`pnpm-lock.yaml` 里 `scheduler@0.23.2` 是 React 的，无关）。

### 5.2 OpenClaw 参照（web 调研）

来源：[Cron Jobs | Claw 文档](https://docs.claw.so/engine/automation/cron-jobs/)（OpenClaw 官方文档站点；另有中文社区 [openclaw.cc/en/cli/cron](https://openclaw.cc/en/cli/cron)、[定时任务 zh-CN](https://docs2.openclaw.ai/zh-CN/cli/cron)）。

要点：

1. **架构**：Cron 跑在 **Gateway 进程内（不是模型内）**；Gateway 常驻运行是前提。
2. **持久化**：任务存 `~/.openclaw/cron/jobs.json`（Gateway 管理，重启不丢）；运行历史 `~/.openclaw/cron/runs/<jobId>.jsonl`（自动裁剪）；可用 `cron.store` 覆盖路径。
3. **三种 schedule**：`at`（一次性时间戳，ISO 无时区则按 UTC）、`every`（固定毫秒间隔）、`cron`（**5 字段 Cron 表达式 + 可选 IANA 时区**，用 `croner` 库；无 `--tz` 时按 Gateway 主机本地时区）。
4. **两种执行风格**：
   - `main`（主会话）：入队一个 **systemEvent**，等下一次 heartbeat（`wakeMode: next-heartbeat` 默认）或立即触发（`wakeMode: now`）——在主会话上下文里跑。
   - `isolated`（隔离会话）：在专用 `cron:<jobId>` 会话里跑一个**独立 agent turn**（每次全新 session id，不继承前次上下文），可选把 summary/full 回帖到主会话（`postToMainMode`）。
5. **结果投递**：`deliver: true` + `channel`（whatsapp/telegram/discord/slack/mattermost/signal/imessage）+ `to`（目标），`bestEffortDeliver` 可选；忽略投递失败可选。
6. **管理**：CLI `openclaw cron add/list/edit/run/remove/runs` + Gateway API `cron.add/update/remove/run/list/status/runs`；`deleteAfterRun` 一次性任务成功后自动删。
7. **配置**：`cron.enabled`（默认 true）、`cron.store`、`cron.maxConcurrentRuns`（默认 1）；`OPENCLAW_SKIP_CRON=1` 全关。
8. **诚实标注**：官方该页**未显式写「错过触发（missed run）的补跑/回填」语义**——它通过 `cron.run <jobId> --force`、`cron.status`、`wakeMode` 机制间接支撑，但没有明文的「停机期间错过 N 次 → 恢复后补跑」规则。本调研未能在官方文档找到该点，按「查不到就标注查不到」处理。

### 5.3 候选实施路径

- **方案 A（推荐）· 桥插件内 in-process 调度器**：在 bridge 新增一个 `scheduler` 模块——文件 KV 任务表（仿 `work.ts`/`deliveries.ts`）+ `ctx.interval`/`setInterval` 轮询（或每任务 setTimeout）+ Cron 解析（引入 `croner` 或 `node-cron`）+ 到期走现有 `agent.inject`/`agent.followup` 注入通道 + 结果经 `deliveries` 台账 + WS 广播推手机。boot/热重载时重 arm，last-run 指纹补跑。
- **方案 B · 外部调度（launchd/cron）调 DSH/桥接口**：早报先例的泛化。launchd/crontab 到点执行脚本 → 调桥的注入端点（**需新增**）或 DSH headless API → 触发 agent 会话。进程外、天然重启存活。
- **方案 C · 启用 DSH 官方 `dsh-schedule`**：在 profile `cordis.patch.yml` 加一个 `schedule` 行（在 `sessions/agents/tools/sessionPersistence` 之后）即可启用。仅提供 after/at/every（≥5min）「会话内提醒」，无 Cron、无移动端通知、session-local。**【状态：已接入（待重启生效）· 用户拍板 #43 第一步，详见 5.4】**

### DSH Schedule 能力清单与限制（接入后实际可得能力）

**能力清单**（三工具，会话范围内，仅 live 根 agent 可用）：

| 工具/规则 | 语义 |
| --- | --- |
| `schedule_create` | 创建一条提醒：`prompt` + 三选一 `after_seconds` / `at` / `every_seconds`（有且只有一项） |
| `after_seconds` | 正安全整数延时（秒），一次性 |
| `at` | 严格 RFC 3339 绝对时刻（`Z` 或 ±HH:MM），或 `{date, time, time_zone}`（time_zone 必填，`UTC` 或 IANA Area/Location）；本地形式 DST 缺口拒绝、重叠取更早一次 |
| `every_seconds` | 固定速率间隔，**≥300s（5 分钟）**，与创建锚点对齐，固定间隔非日历规则 |
| `schedule_list` | 按创建顺序返回活动记录，含 `state: scheduled|overdue` 与 `deliveryMode: session-local` |
| `schedule_delete` | 按 `schedule_id` 删除活动记录；未知 id 返回 `{deleted:false, code:"schedule_not_found"}` |
| 到期交付 | 一次性→`[SCHEDULE REMINDER]` framing 各入队一条 follow-up；Every 逾期→`[SCHEDULE REMINDER BATCH]` 单条批量 framing；`agent.followup()` 在 agent 完全 idle 后开普通后续轮次，不打断当前对话 |

**限制清单**：

| 限制 | 说明 |
| --- | --- |
| **无 Cron 表达式** | 「日历表达式或 Cron 表达式不在协议内」（`README.zh.md:114`） |
| **session-local 交付** | 仅原会话 live 时准时运行；**冷会话无外部通知**，恢复后才处理 overdue（`README.zh.md:111`） |
| **错过只补最新** | 逾期 Every 只贡献最新一个发生时点，不回放积压（`README.zh.md:115`） |
| **every 下限 5 分钟** | `frequency_too_high` 错误（`every_seconds < 300`） |
| **无手机通知** | Schedule 只有会话内 follow-up 文本，无独立 UI/回执，**不经桥的 WS 推送**（`README.zh.md:43`） |
| 崩溃重复窗口 | follow-up 准入后、dispatch 检查点前崩溃可能重复（at-least-once，`README.zh.md:116`） |
| 加载顺序边界 | 加载时已存在的 agent / 运行时子 agent 不获得 Schedule（`README.zh.md:117`） |
| 活动驱动重试 | 到期 preflight 被拒无私有重试 timer，靠后续活动触发重算（`README.zh.md:112`） |

> **一句话定位**：`dsh-schedule` 是「会话内持久提醒」，满足"同一会话里延时/定点提醒"，但**不满足**"跨会话定时任务 / Cron / 冷会话主动触发 / 结果推手机"——后者仍按本调研第七节推荐走方案 A（桥内调度器）。

## 六、多方案优劣势对比

| 维度 | 方案 A（桥内调度器） | 方案 B（外部 launchd/cron） | 方案 C（DSH 原生 schedule） |
| --- | --- | --- | --- |
| DSH 插件 API 是否允许 | ✅ 允许。`cordis-plugin-timer` 已接入（base patch `timer` 行），桥已在用 `setInterval` 长驻（`core.ts` 多处） | ✅ 不依赖插件 API，进程外 | ✅ 官方插件，函数插件 `{name,inject,apply}`（`index.js:1343-1387`） |
| Cron 表达式 | ✅ 引入 `croner`/`node-cron` 即可，功能完整 | ✅ launchd/cron 原生 | ❌ **无 Cron**（`README.zh.md:114`）；`every_seconds` 下限 300s |
| 持久化与重启存活 | ✅ 任务表文件 KV（仿 work.json/deliveries.json），boot 重 arm | ✅ 天然进程外，操作系统级可靠 | ✅ 会话日志 `schedule/change` + sessionPersistence |
| 错过补跑 | ✅ 可自定义（last-run 指纹 + 策略） | ✅ 取决于调度器配置（cron 无补跑；launchd `StartCalendarInterval` 跳过） | ⚠️ 仅「只追赶最新一次」，不回放积压（`README.zh.md:115`） |
| 时区/夏令时 | ✅ croner 自带 IANA/DST | ✅ launchd/cron 走系统时区 | ✅ `at` 显式 `time_zone`，DST 缺口拒绝、重叠取早（`README.zh.md:25`） |
| 触发 agent 会话 | ✅ 复用 `agent.inject`/`followup`（`core.ts:842-867`） | ⚠️ 需**新增 HTTP 注入端点**（现无），或走 headless | ✅ `agent.followup`（`index.js:835`） |
| **移动端联动（结果推手机）** | ✅ **原生打通**：结果 → deliveries 台账 + WS 广播 → 手机通知（复用 v0.15 补投递） | ⚠️ 需另接注入 + 推送链路 | ❌ **session-local**：冷会话不触发、无推送（`README.zh.md:111`） |
| 实现成本 | 中（新增 scheduler 模块 + 1 个 cron 库依赖） | 中低（launchd plist + 1 个注入端点） | 低（加 1 行 patch）但能力不足 |
| 风险 | 热重载/重启丢 in-memory 定时器（已有 dispose→re-arm + work.json 续跑先例，可控） | 进程不在时的拉起链路复杂；与 DSH 会话耦合需自定义 | 能力不足，仅作会话内轻提醒 |
| 维护 | 自有代码，需自测/自维护 | 依赖系统调度 + 自建注入 | 官方维护，随 DSH 升级 |

> 每条结论均可在 5.1/5.2 找到事实来源；不凭印象。

## 七、最终选择与决策逻辑

**推荐：以方案 A 为主，方案 C 作为「会话内轻提醒」可选补充，方案 B 作为「进程冷启动」兜底。**

- **为何主选 A**：
  1. **功能满足度唯一全绿**：Cron 表达式、持久化、错过补跑、时区/DST、触发会话、移动端通知——只有 A 能全量覆盖（对照需求点 1~7）。
  2. **复用最大化**：桥已具备 A 所需全部原语——文件 KV（`work.ts`/`deliveries.ts`）、注入通道（`agent.inject`/`followup`）、WS 推送、deliveries 补投递、热重载 dispose→re-arm。A 只是「新增一个 scheduler 模块」，不造新轮子。
  3. **移动端联动是硬需求**（铁律 9 移动端优先 + 通知补投递刚建）：只有 A 能天然把「定时任务结果」接到手机；C 是 session-local、冷会话不触发，直接不满足。
  4. **规避 DSH 原生两大短板**：无 Cron、session-local。
- **为何不单用 C**：无 Cron、`every` 下限 5 分钟、session-local 冷会话不触发、无移动端通知通道——它是「提醒」不是「定时任务」。
- **为何不主选 B**：可靠但「外挂」——需新增 HTTP 注入端点、与 DSH 会话/鉴权耦合、移动端通知需另接；仅适合做进程不在时的冷启动兜底，不适合做主调度面。
- **为何保留 C**：「会话内让 agent 20 分钟后提醒我」这类轻场景，官方实现零维护，接入成本极低（1 行 patch），值得作为 A 的轻量补充。**（用户拍板 #43 第一步已接入，见 5.4。）**
- **为何保留 B**：每日早报等「DSH 进程可能不在」的场景，launchd 进程外可靠，作为 A 的守护/冷启动层。

> **由谁拍板**：本方案为调研论证，最终由用户拍板（铁律 1）。拍板后同一轮记入 `docs/decisions/决策台账.md` 并送达实现子代理。

## 八、对现有架构的影响

- **改动面**：bridge 新增 `scheduler` 模块（任务表文件 KV + 轮询/定时 arm + cron 解析 + 注入触发 + 补跑），新增 HTTP 路由 `/remote/cron/*`（list/create/delete/run-now，供移动端与手工管理），引入 1 个 cron 库依赖（`croner` 或 `node-cron`）；移动端 App 增设定时任务列表 UI（若做管理面）。
- **协议**：`protocol.ts` 增 ServerEvent（定时任务触发/结果）与客户端管理消息；沿用服务端投影单向数据流。
- **风险点**：
  1. **热重载丢 in-memory 定时器**：必须「文件持久化 + boot/热重载重 arm + last-run 补跑」三位一体（桥已有 work.json 续跑先例，风险可控）。
  2. **崩溃重复窗口**：触发点与 last-run 落盘之间崩溃可能重复触发一次（at-least-once 语义，与 DSH schedule 同类窗口，`README.zh.md:116`）。
  3. **注入语义选择**：运行中会话用 `agent.inject`（不打断）、空闲用 `agent.followup`（唤醒），需按 `agent.status` 分支（`core.ts:861-867` 已有此模式）。
- **兼容与回滚**：纯增量模块，不破坏现有消息/队列/通知链路；回滚 = 摘除新模块与路由即可。DSH 原生侧方案 C 已在 profile patch 加 `schedule` 行（可逆：删掉该 insert 行即回滚，见 5.4）。

## 九、后续迭代规划

- **P1（MVP）**：桥内 scheduler 模块——任务表文件 KV + Cron 解析（`croner`）+ `ctx.interval` 轮询 + 到期 `agent.inject`/`followup` 触发 + 结果走 deliveries 补投递推手机；提供 `/remote/cron` 的 list/create/delete/run-now。
- **P2**：错过补跑（last-run 指纹 + 补跑策略：补跑最新一次 / 全部 / 不补）+ 时区/DST 单测 + 移动端定时任务列表/开关 UI。
- **P3**：接入 DSH 原生 `dsh-schedule`（会话内轻提醒，可选）**【第一步已接入，见 5.4】** + launchd 冷启动兜底 + 收窄崩溃重复窗口。
- **触发再评估**：DSH 官方若将 `dsh-schedule` 升级为进程级 Cron（支持表达式 + 跨会话 + 通知），届时重新评估 C → 是否下沉到官方能力。
