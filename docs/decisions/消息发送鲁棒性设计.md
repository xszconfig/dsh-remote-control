## 一、需求背景

- 为什么做：用户要求系统梳理「消息发送模块」在弱网/频繁断连下的可靠性，回答「是否 100% 可靠、哪些情况会出问题、可能解法」，先交评审再实施。P00 修复解决了「失败/发送中不丢」，但没有回答「送达是否可信、重试是否重复、失败是否可感知」。
- 边界（做什么/不做什么）：
  - 做：发送链路全路径梳理 + 弱网边界枚举 + 可靠性结论 + 消息可靠性协议/状态机/幂等的字段级设计。
  - 不做：连接层的多通道选型（LAN/frp/WebRTC 已在《网络连接与弱网可靠性调研》§2 处理，本文档只引用结论）；UI 视觉设计；本次不写实现代码。

## 二、核心需求点拆解

1. 每次用户点击发送的消息，无论结果如何，客户端都**持久化**（发送前落盘）——已由 P00 修复覆盖，本文档确认其作为底座。
2. 每次发送的结果**可被客户端确定性地判定**：成功=服务端已接受；失败=服务端未接受（或结果未知），必须显式 ❗，不得静默消失。
3. 重试**幂等**：同一条用户消息重发 N 次，服务端最多投递 1 次（业务语义上的「恰好一次」）。
4. 服务端回显与本地 pending 的匹配**精确**（不再靠文本+时间模糊匹配），杜绝「双份显示/漏删」。
5. 断线重连后，未确认消息可**自动补投**（带重试上限与显式失败），不依赖用户逐个手动点 ❗。
6. 运行中消息进排队队列后，其**状态可见性**与 idle 分支一致（成功/失败/排队中都有明确反馈）。

## 三、核心指标拆解

| 指标 | 目标 | 达标口径 | 测量方法 |
| --- | --- | --- | --- |
| 假送达消除率 | 100% 消除「帧已写但服务端未接受」被误判为成功 | 每次发送以服务端 `ack` 为准，超时未 ack 转 failed | mock-bridge 注入「收到帧但不应答」断言 |
| 静默失败归零 | 服务端异步拒绝（not_running 等）必映射到 ❗ | 服务端 `error{msgId,code}` 与 pending 精确关联 | mock-bridge 回 not_running 断言 ❗ |
| 重复投递率 | 同 msgId 重发 N 次，服务端投递 ≤1 次 | bridge 侧 msgId 去重窗口内幂等 | mock-bridge 重发同 msgId 断言队列只有 1 条 |
| 回显匹配精度 | 100% 精确（不靠文本+时间） | 回显携带 clientMsgId，按 id 匹配 | mock-bridge 连续两条同文本断言各自匹配 |
| 断线补投 | 重连后未 ack 消息自动重放 | 重连 hello 后自动重放队列，上限 3 次 | mock-bridge 断连→重连→断言补投 |
| 队列持久化上限 | 单会话待发送 ≤ 64 条，防止无界增长 | 超出丢弃最旧并记日志 | 单测 |

## 四、预期收益

- 对用户：消息发送从「至少一次 + 可能静默丢」升级为「可感知失败 + 幂等重试」，弱网下不再出现「以为发了其实没发」或「一条消息变两条」。
- 对稳定性：把发送结果判定从「帧写入」收紧到「服务端接受」，消除假连接（~50s 无感）期间的全部误判。
- 对开发：消息状态机从「连接生命周期」收敛为「消息生命周期」，状态归属清晰、可单测。

## 五、技术方案设计

### 5.1 现状发送链路全路径（App + bridge，实证）

```
输入框点击发送
  └─ BridgeClient.sendMessage(text)
       ├─ running 会话：乐观 queueItems += local-<millis>（进排队面板，不上屏）
       └─ idle 会话：pending = PendingMessage(localId, sessionId, text, Sending)
                     └─ scope.launch:
                          └─ connection.send(send_message{sessionId,text})
                               ├─ true  → markPendingSent（已送达，等回显接棒）
                               └─ false → markPendingFailed（红❗） + 回滚 local- 排队项
服务端 bridge（core.ts send_message handler）：
  └─ agentOf(sessionId) 无 → resumeAgent 自动打开 / deliverSubagent（子代理）→ 失败回 error{not_running/...}
  └─ 斜杠命令 → commands.execute（不回 user_message 回显，走 command/run+command/done）
  └─ 普通文本 → a.followup(createUserMessage({content, source:{kind:'user'}}))  ← 无 ack、无客户端 id
回显（projectEvent）：
  └─ user/message → 投影为 user_message{seq,timestamp,text,source}（无 clientMsgId）
客户端 handleEvent：
  └─ matchPendingEcho(同会话 + 同文本 + |echoTs-createdAt|<60s) → 命中 removePending
```

### 5.2 关键现状事实（决定方案边界）

- `ConnectionManager.send()` 返回 `Boolean`：`ws==null` → false；`session.send(Frame.Text(...))` 抛异常 → false；否则 true。**true = 帧写入未抛异常，≠ 服务端已接受**（半开连接/隧道假连接下帧写成功但网络层已死）。
- 协议 `send_message{sessionId,text}` **无 msgId/无 ack/无序号**（`protocol.ts:237`、`Protocol.kt:686`）。
- `createUserMessage` 的签名 `id?: never`（`@deepseek-ai/dsh-llm` message.d.ts:171）——**客户端无法把 msgId 写入 harness 消息身份**，harness 消息 id 由服务端生成。幂等键只能落在 bridge 中继层。
- 回显投影 `user_message` 只带 `{seq,timestamp,text,source}`（core.ts:2721），**不带 clientMsgId**；文本被斜杠命令路由/服务端规范化后，回显文本 ≠ 发送文本 → 现有「文本+60s」匹配会漏删（pending 残留 + 回显双份）。
- 服务端 `error{not_running/command_failed/subagent_unavailable}` 是**异步**事件，客户端 `handleError` 只弹横幅、不关联回 pending → 消息已 markPendingSent，**永久停在「已送达无图标」，用户无感失败**（静默失败）。
- 服务端 work.json 的 `restoreQueueIfLost` 按 `id` 或 `text` 去重（core.ts:1033）——只用于**服务端自己重启后**的排队恢复，**不覆盖客户端重试**（客户端重发 = 新的 send_message = 新的 followup = 重复投递）。
- P00 修复后：pending 落盘（Sending/Failed）、重启恢复 sending→failed、成功即删、回显命中即删。**但「成功」仍是帧写入成功，不是服务端接受**。

### 5.3 可靠性结论（诚实）

**当前做不到「恰好一次」，只做到「至少一次 + 客户端持久化」，且存在静默失败路径。**
- 已解决（P00 修复）：失败/发送中不丢（落盘+恢复）。
- 未解决：① 假送达（帧写成功≠接受）；② 服务端异步拒绝的静默失败；③ 重试幂等（重复投递）；④ 回显模糊匹配（双份/漏删）；⑤ 运行中排队分支的半开丢失无 ❗；⑥ 无自动补投。
- 「100% 可靠」在分布式消息里本不存在（两将军/CAP）；工程目标是 **「可感知的失败 + 幂等重试」把端到端语义收敛到「恰好一次」的业务等价**。要做的是把「结果未知」从「静默」变成「显式 ❗」，并用 msgId 幂等把「重试」从「可能重复」变成「不会重复」。

### 5.4 目标协议与状态机（字段级设计）

**消息身份**：客户端在 pending 创建时生成 `msgId`（沿用现有 `localId` 的 `pending-<millis>-<seq>` 即可，或独立 UUID；要求：同会话内唯一、跨重启稳定——落盘后随消息走）。`PendingMessage` 增加 `msgId` 字段（与 `localId` 可合一，减少概念）。

**协议升级（App + bridge 双端镜像）**：
```
CmdSendMessage { type:'send_message', sessionId, text, msgId }
EvAck          { type:'ack', msgId, sessionId, ok:true }
EvError        { type:'error', code, message, msgId? }   // msgId 可空，有则精确关联
EvEvent.user_message 投影增加 clientMsgId?: string       // 回显精确匹配用
```

**bridge 幂等去重（中继层，不依赖 harness id）**：
- 维护 `clientMsgId → { sessionId, harnessMsgId?, status:'pending'|'delivered', at }` 映射（内存 LRU + 持久化进 work.json 的 `msgIds` 段，重启存活）。
- `send_message{msgId}` 到达：若 msgId 已存在且 `delivered` → 直接回 `ack{msgId,ok}`，不重复 followup（幂等）；否则 followup 后记录 `harnessMsgId = 返回值.id`，回 `ack{msgId,ok}`。
- 去重窗口：`msgId` 保留 24h 或单会话最近 256 条（LRU），超窗视为新消息（与「同文本连续快速发两条」语义兼容——两条 msgId 不同，不误判）。

**回显精确匹配**：bridge 在 projectEvent 的 `user/message` 分支读取 `event.data.id`（harness 消息 id），反查 `harnessMsgId→clientMsgId` 映射，把 `clientMsgId` 注入投影。客户端 `matchPendingEcho` 改为**按 clientMsgId 精确匹配**，fallback 到文本+时间（兼容旧 bridge）。

**ack 超时与重试**：
- 客户端发送后进入 `Sending → 等 ack`；超时阈值 `ACK_TIMEOUT_MS = 3s`（弱网下 1 次 RTT 上限的量级），超时转 `Failed`（结果未知）。
- `Failed` 手动点 ❗ 重发沿用同一 `msgId`（幂等前提）。
- 自动补投（可选阶段）：重连 hello 后，对仍为 `Sending`/`Failed` 且 `retryCount < 3` 的 pending 自动重发同一 msgId；达上限转 `Failed` 并停发。

**落盘格式**（在 P00 修复的 `PendingStore` 上扩展）：
```json
[{ "msgId":"pending-...-0","sessionId":"...","text":"...","status":"Sending","createdAt":123,"retryCount":0 }]
```
- `status` 语义：`Sending`（已落盘待确认）、`Sent`（已 ack，等回显，**不落盘**）、`Failed`（未 ack/超时/异常）。
- 队列容量上限：单会话 ≤ 64 条，超出丢最旧并记日志（防无界增长）。
- 重启恢复：`Sending`/`Failed` → 恢复为 `Failed`（结果未知，不自动重发，交用户点 ❗）——与 P00 修复语义一致；若启用自动补投，恢复后再走自动补投逻辑。

**运行中排队分支闭环**（补齐可见性）：
- 运行中消息不再只进 `queueItems` 乐观项：同样生成 msgId 并落盘一个 `PendingMessage(status=Sending)`（但不渲染上屏气泡，只渲染排队面板）。
- `session_queue` 到达且含该 msgId 对应项 → 视为服务端已接受（等效 ack），落盘删除 + 移除乐观项。
- 超时未在 `session_queue` 见到 → 转 Failed 并在排队面板/列表行显示 ❗。

## 六、多方案优劣势对比

| 维度 | 方案A 最小增强（持久化+状态机闭环+回显匹配强化，不加协议） | 方案B 客户端 msgId + bridge 幂等去重 + ack（协议升级） | 方案C 端到端 ack（含 agent 处理完成回执） |
| --- | --- | --- | --- |
| 成熟度/发布节奏 | 纯客户端改动，零协议风险，快 | 需 App+bridge 双端协议镜像，中等 | 需 harness 侧处理完成回执，重、慢 |
| 功能满足度 | 解决「失败可感知/不丢」，**不解决假送达/幂等/静默失败** | 解决假送达/幂等/回显精确/静默失败，命中核心需求 3/4/5 | 额外提供「agent 已处理」回执，超出控制面需求 |
| 性能/资源 | 无新增 | bridge 增加 msgId 去重映射（内存 LRU + work.json 段） | ack 等待与重试链更长 |
| 接入/迁移成本 | 低（改 App 状态机 + 测试） | 中（App 协议 + bridge 去重 + 投影注入 + 双端测试） | 高（涉及 harness 会话事件链） |
| 维护风险 | 低 | 中（去重窗口/LRU/映射一致性需单测） | 高（回执语义与 harness 耦合） |
| License | 无 | 无 | 无 |
| 事实依据 | `ConnectionManager.kt`、`BridgeClient.kt` 现状 | `createUserMessage id?: never`（dsh-llm message.d.ts:171）→ 幂等只能落 bridge 层；`projectEvent` 可读 `event.data.id` 注入 clientMsgId | 微信/Telegram 的 ack+seq 是全链 ack 的行业参照（《弱网可靠性调研》§1.3） |

## 七、最终选择与决策逻辑

- **方向已由用户于 2026-09-07 拍板**（`AGENTS.md` 历史决策「连接与弱网可靠性」）：① send_message 升级 msgId+ack+幂等去重（bridge v0.14）；② 本地消息队列=文件 KV 持久化 + 断线自动重放（上限/超时转显式失败红❗，at-least-once）；③ 应用层 ping/pong 判活 + bridge LAN 二级 WS 监听 + mDNS；④ frp/VPS 暂不租；⑤ 弱网模拟器=mock-bridge 注入为主；⑥ 演进顺序=消息底座→LAN→frp→弱网模拟。
- **本文档落地结论 = 方案 B（msgId + bridge 幂等去重 + ack）+ 方案 A 状态机闭环底座**，与拍板方向 ①② 完全一致；方案 C（agent 处理完成回执）不在本阶段（控制面不需要，与拍板「消息底座优先」一致）。
- 理由（对照第六节）：方案 A 是 B 的必要前置（状态机/文件 KV 落盘已由 P00 修复完成大半）；B 用最小协议增量一次性根治「假送达/幂等/静默失败」三大 P0 缺口，成本可控、无新依赖、与已拍板方向同源。C 超出「消息必达」边界，留作远期观察。
- 本文档新增的字段级默认值（ack 超时 3s、去重窗口 24h/256 条、重放上限 3 次、单会话队列上限 64 条）为**实施建议值**，非重大选型，实施前与主对话/用户对齐即可。

## 八、对现有架构的影响

- 改动面：
  - App：`protocol.kt`（CmdSendMessage 增 msgId、新增 EvAck、EvError 增 msgId、EventProjection 增 clientMsgId）；`PendingMessages.kt`（加 msgId/retryCount、ack 超时状态机、回显按 id 匹配）；`BridgeClient.kt`（发送/重试/回显/重连补投闭环）；`PendingStore` 落盘格式扩展。
  - bridge：`protocol.ts`（同镜像）；`core.ts`（send_message 幂等去重 + ack + error.msgId + projectEvent 注入 clientMsgId + work.json 增 msgIds 段）。
- 风险点：① msgId 去重窗口的 LRU/持久化一致性（需单测）；② 旧版客户端/旧版 bridge 的兼容（ack 字段缺省、msgId 缺省 → 回退文本+时间匹配）；③ harness 消息 id 与 clientMsgId 的映射在「消息被消费/历史翻页」后的生命周期（映射可随去重窗口过期）。
- 兼容与回滚：协议字段全部向后兼容（msgId 缺省时走旧逻辑）；bridge 的 ack/去重可开关（env 逃生门），出问题一键回退到「无 ack」现状。

## 九、后续迭代规划

- 阶段 1（P0）：方案 A 底座确认（P00 修复 merge）+ 方案 B 核心（msgId+ack+幂等+回显精确）。

3. 应用层 ping/pong 判活（假连接秒级判死）+ bridge LAN 二级 WS 监听 + mDNS（保留鉴权）。
4. frp/VPS 暂不租（Tailscale 过渡保留）。
5. 弱网模拟器 = mock-bridge 注入为主 + TCP 代理为辅。
6. 演进顺序 = 消息底座 → LAN → frp → 弱网模拟。

**字段级默认值（实施建议值，待对齐）**
- `msgId` 生成：复用现有 `localId`（`pending-<millis>-<seq>`），跨重启稳定（随落盘走），不另起 UUID。
- `ACK_TIMEOUT_MS`：3s（弱网单次 RTT 上限量级）；超时转 Failed（结果未知）。
- 去重窗口：单会话最近 256 条 LRU 或 24h TTL，取先到者；bridge 侧映射持久化进 work.json 的 `msgIds` 段。
- 断线自动重放：重连 hello 后重放未 ack 消息，上限 3 次，达上限转 Failed 停发。
- 单会话待发送队列上限：64 条，超出丢最旧并记日志。
- 运行中排队分支是否纳入同套 msgId/ack 闭环（需求 6）：建议阶段 2 纳入（与拍板「消息底座」同源），阶段 1 先做 idle 分支。
