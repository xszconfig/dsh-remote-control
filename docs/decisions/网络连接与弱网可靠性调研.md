# 网络连接与弱网可靠性调研

> 日期：2026-09-08 ｜ 状态：调研完成，已拍板（2026-09-07，见决策台账 #15） ｜ 只读调研，未改码、未 commit
> 关联文档：《消息发送鲁棒性设计》（在途，尚未落盘）——本调研聚焦「连接层 + 弱网」与「消息可靠性最佳实践」的外部证据与方案权衡，具体消息可靠性协议的字段级设计留给该设计文档，两者交叉引用。

## 0. 现状基线（App + Bridge 代码实证，非推测）

| 维度 | 现状 | 证据 |
|---|---|---|
| 传输 | 单条 WebSocket `ws://<host>:3080/remote/ws`，桌面 dsh 只绑 127.0.0.1，无线经 `tailscale serve --tcp=3080 tcp://localhost:3080` 终结回环 | `docs/connection-architecture.md` |
| 多候选 | 二维码/设备注册下发多端点（127.0.0.1 + 局域网 + Tailscale IP），逐候选 4s 快速失败回退 | `docs/connection-architecture.md` §5 |
| 心跳 | 仅 OkHttp `pingInterval(30s)` 协议层 PING；**无应用层 ping/pong**、客户端无 pong 判死 | `docs/connection-architecture.md` §3 |
| 假连接实测 | `adb reverse --remove` 后双方 ~15s 无感，靠 pong 超时 ~50s 才判死切路（隧道静默死亡） | `docs/connection-issues.md` 2026-08-29 |
| 自动重连 | 指数退避 1s→30s，仅限「有凭据」连接，幂等守护；重连后 hello 补发挂起队列 | `docs/connection-architecture.md` §6 |
| 发送协议 | `send_message{sessionId,text}` **无 msgId / 无 ack / 无序号 / 无幂等键** | `Protocol.kt` §ClientCommand / bridge `protocol.ts` §CmdSendMessage |
| 发送状态机 | `PendingMessages`：Sending/Sent/Failed，**纯内存**（`_session` state），回显去重用「同会话+同文本+60s 窗口」模糊匹配 | `PendingMessages.kt`、`BridgeClient.kt:797-869` |
| 「已送达」语义 | `connection.send()` 返回 true = **WS 帧写入未抛异常**，**不等服务端已处理**（socket 立即死仍返回 true → 假送达） | `ConnectionManager.kt:146-159` |
| 服务端处理 | bridge `send_message` → `agentOf` → 自动 resume → `followup`；**不回 ack**，手机只能靠会话事件流里的 user_message 回显判断 | bridge `core.ts:1861-1922` |
| 持久化 | pending 消息**不落盘**，杀进程即丢；无断线自动重发（仅手动点❗） | `BridgeClient.kt:853-869` |
| 测试桩 | `tools/mock-bridge`（ws + 内存 session/事件），**无可配置弱网能力** | `tools/mock-bridge/mock-bridge.mjs` |

**结论**：当前可靠性缺口集中在「假连接/假送达（无 ack + 无应用层判活）+ 无持久化队列 + 无幂等序号 + 无断线自动重发」，四者是「微信级无感可靠」的共同前置，也是本报告 C 部分的改造靶点。

## 1. 调研 A：IM 类 App 弱网消息可靠性最佳实践

### 1.1 各家矩阵总览

| 产品 | 长连接/多通道 | 心跳与快速重连 | 本地缓存/落盘 | 重试·幂等·序号·ack | 状态展示 UX | 坑点（假连接/重复/丢序/静默丢） |
|---|---|---|---|---|---|---|
| 微信 | 自研 mars：STN 长连+短连混合，多 IP/端口智能排序 | 长连心跳保活 + NAT 穿透 + 断线自动重连（mars 实测弱网连接存活 99.992%） | 本地 SQLite 消息库，收发落盘 | SYNC 协议 + SyncKey 增量同步；客户端确认收到后 HTTP 上报新 SyncKey；服务端消息序号 | 发送中（转圈）→已发送→失败（红❗点击重发）→已读回执 | 弱网重复/丢序由序号+SyncKey 收敛；长连与短连并存互为兜底 |
| 飞书 | 官方不公开长连接内部实现；网关经 WebSocket 长连推送（第三方 hermes-agent 有「飞书 websocket ping 超时可调」佐证其 WS 长连形态） | WS ping 定时可调；断线重连 | 客户端本地消息缓存（IM 通用） | 接口层「服务端可能已接收但客户端未拿响应」的模糊场景下**简单重试会产生重复消息**——需幂等键 | 发送中/已读/失败 | 公开资料最少；模糊重试重复消息是官方接口层的已知坑 |
| Telegram | MTProto over TCP/HTTP（多 DC、连接可迁移） | 周期性 ping；服务端会推 `msg_id`/`seq_no` 供重连对齐 | 云端为主 + 本地缓存 | `msgs_ack` 显式确认；`msg_id` 唯一且单调、`seq_no` 防丢序；`msg_container` 批量；丢失自动重发 | 单勾/双勾（送达/已读） | 无权威协议规范（IEEE 论文），但 ack/seq 机制是公开事实 |
| WhatsApp | Signal/WhatsApp 自建长连（XMPP 演进 + 自有协议），多数据中心 | 心跳 + 重连；离线消息由服务端队列兜底 | 本地加密数据库 + 服务端离线队列 | at-least-once + 服务端离线队列 + 消息 id 去重（重试不重复） | 单勾/双勾/蓝色双勾（发送/送达/已读） | 依赖服务端离线队列，弱网丢消息由服务端重投 |
| Claude Code Remote Control | 官方 Remote Control（手机/浏览器为远程窗口，执行在本机），WebSocket relay | 自动重连；官方明确「重连期间队列化消息/权限提示/状态更新，恢复后补投」 | 重连期间本地队列化 | 断线补投（队列 + 重放） | 连接/断线横幅 | 多个 issue 反映**静默断连不恢复**、WS relay 反复重连、断连会话消息**永久排队** |
| Codex App（OpenAI） | 官方远程会话（手机接管桌面会话） | — | 无明显本地队列 | 无 | — | 官方 issue：**断连丢草稿文本/语音输入、需整体重连**；断连时 thread/resume 响应到不了客户端 |

### 1.2 逐家要点（带来源）

**微信（腾讯 mars / SYNC）**
- 微信网络层自研 `mars`：STN（长连 + 短连混合、网络自动切换/断线重连）、SDT（网络诊断）、xlog（高性能日志），官方开源并成文《微信终端跨平台组件 Mars 系列》（[WeMobileDev/mars](https://github.com/Tencent/mars) 官方文章：Mars 系列（三）连接超时与 IP&Port 排序 [腾讯云](https://cloud.tencent.cn/developer/article/2220261)）。
- 弱网下长连接保活的工程实践（心跳、NAT 穿透、断线自动重连，实测 99.992% 存活）见 [datasea.cn 整理](https://datasea.cn/go0708641721.html)。
- 消息同步用 **SYNC + SyncKey 增量同步**：客户端拉到新消息后**再次 HTTP POST 上报确认 + 拉取最新 SyncKey**（[微信 App 通信协议案例学习](https://www.e-com-net.com/article/1666854421604163584.htm)）；服务端海量消息用**消息序号**做全局有序与去重（[52im.net：微信 IM 消息序列号生成实践](http://www.52im.net/forum.php?mod=viewthread&tid=1998)）。
- ACK 与重传的通用机制见 [IM 消息必达性设计 ACK 机制与重传策略全解析（oschina）](https://my.oschina.net/emacs_7987827/blog/19423635)。
- 网络整理与思考的一手文章：[《微信网络技术的一些整理与思考》](https://mp.weixin.qq.com/s/SHQay5wlz2fQ1xwQoh5eBA)。

**飞书（Lark）**
- 飞书 IM 长连接内部实现**未见官方公开技术博客**，公开可考的是：第三方 agent 框架（hermes-agent）对飞书提供「websocket ping 超时覆盖」配置（[NousResearch/hermes-agent commit](https://github.com/NousResearch/hermes-agent/commit/ea31d9077c1109f94fde5b97cd92e7920f5a3d18)），佐证其长连为 WS + 可调 ping 的形态。
- 接口层「网络模糊场景（服务端已收、客户端未得响应）下简单重试会**产生重复消息**」是官方接口的已知约束，需业务侧幂等（[cc-linker 产品设计文档](https://github.com/yujuntea/cc-linker/blob/master/docs/%E4%BA%A7%E5%93%81%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3-%E8%87%AA%E5%BB%BA%E6%96%B9%E6%A1%88.md)）。
- 结论：飞书对外不承诺「无重试不重复」，把幂等责任下放到调用方——这条与本项目「send 成功后可能已投递给 agent」的边界高度一致，**必须自己加幂等键**。

**Telegram（MTProto）**
- 官方文档《Service Messages about Messages》明确：`msgs_ack`（确认）、`msg_id`（唯一、客户端/服务端各持单调生成）、`seq_no`（防丢序/防重放）、`msg_container`（批量发送），是「弱网必达」的教科书级参考（[core.telegram.org 官方](https://core.telegram.org/mtproto/service_messages_about_messages)，镜像 [web.archive.org](https://web.archive.org/web/20240206073402/https://core.telegram.org/mtproto/service_messages_about_messages)）。
- 开源客户端 Telethon 的 `mtprotosender.py` 直接体现 msg_id 生成与 ack 处理（[Telethon 源码](https://github.com/LonamiWebs/Telethon)）。
- 坑点：协议无权威公开规范（[IEEE 论文：Four Attacks and a Proof for Telegram](https://ieeexplore.ieee.org/document/9833666)）。

**WhatsApp**
- 服务端离线队列 + at-least-once + 消息 id 去重，断网时消息先落服务端队列、恢复后投递（[dev.to: How WhatsApp Works Without Internet](https://dev.to/kishanag028/how-whatsapp-works-without-internet-offline-messaging-and-sync-explained-4c3n)、[llm-driven-system-design/whatsapp 架构](https://github.com/evgenyvinnik/llm-driven-system-design/blob/main/whatsapp/architecture.md)）。
- 启示：**「不通先缓存」的缓存点放在哪里**——WhatsApp 放在服务端离线队列（手机不可达时服务端代收）；本项目「手机是发送方、桌面是收方」，缓存点应在**手机本地**（发送前落盘），等价于把离线队列前置到发送端。

**Claude Code Remote Control（最直接的同类参照）**
- 官方原话：断线/重连期间「*queues messages, permission prompts, and status updates... delivers them once the connection recovers*」（本仓库竞品档案已引，见 `docs/competitor-research/ClaudeCode与Cursor竞品档案.md` §L68-70）。
- 官方 issue 反例：`#34255` 自动重连失败、连接**静默丢失无恢复**；`#33232` remote-control WebSocket relay 反复重连、命令挂起；`#91087` 崩溃服务端会话永不回收、断连会话消息**永久排队**（[#34255](https://github.com/anthropics/claude-code/issues/34255)、[#33232](https://github.com/anthropics/claude-code/issues/33232)、[#91087](https://github.com/anthropics/claude-code/issues/91087)）。
- 启示：连「巨头官方」都在假连接/静默丢上翻车，说明**判活 + 补投 + 队列超时兜底**三者缺一不可。

**Codex App（OpenAI）**
- 官方 issue：`#36537` 连接中断时**丢失草稿文本/语音输入**且需整体重连；`#39931` 断连导致 thread/resume 响应到不了客户端（[#36537](https://github.com/openai/codex/issues/36537)、[#39931](https://github.com/openai/codex/issues/39931)）。
- 启示：**「未发送草稿」与「已发送待确认消息」都要本地落盘**，断连只影响传输不影响内容。

**OpenClaw（原 Clawdbot）**
- 网关多通道（WhatsApp/Telegram/飞书/iMessage）+ 手机/桌面 App，消息模型见官方文档（[OpenClaw Messages](https://docs.openclaw.kr/concepts/messages) / [中文站](https://openclaw.cc/concepts/messages)）。
- 坑点 issue：`#1922` Android WS 握手竞态；`#75882` 网关 event-loop stall 导致跨通道延迟、漏回复、通道断连；PR `#98385` 移动端协议不匹配需可恢复提示（[#1922](https://github.com/openclaw/openclaw/issues/1922)、[#75882](https://github.com/openclaw/openclaw/issues/75882)、[#98385](https://github.com/openclaw/openclaw/pull/98385)）。
- 启示：**网关单点/单 event-loop 是断连与漏消息的集中来源**；本项目 bridge 单进程也有同类风险（bridge 挂则手机全断）。

**WorkBuddy（CodeBuddy）**
- 官方「远程控制」文档强调**保持 tunnel 域名稳定**、桌面端默认开「允许锁屏远程」以维持长连（[CodeBuddy 远程控制](https://www.codebuddy.cn/docs/cli/remote-control)、[多端协同（连接电脑）](https://www.codebuddy.cn/docs/workbuddyapp/features/Multidevice)）。
- 启示：第三方 tunnel 是「需要主动维护」的脆弱点，与用户痛点①同源。

### 1.3 共性归纳（可直接照搬到本项目的 6 条）

1. **发送前落盘、发送后确认**：发送方本地持久化队列是「不通先缓存」的地基（微信 SQLite / WhatsApp 服务端队列 / Claude Code 重连队列）。
2. **消息级 ack + 唯一序号 + 幂等键**：`send 成功` ≠ `服务端已处理`，必须服务端回 ack（含 msgId），重发靠同一 msgId 幂等去重（Telegram msgs_ack / 飞书幂等键教训）。
3. **应用层判活，别只信 TCP/协议心跳**：隧道类网络无 FIN/RST，必须双向应用层 ping/pong + 超时判死（本项目 2026-08-29 实测 ~50s 假连接，与 Claude Code #34255 同类）。
4. **快速重连 + 断线补投 + 队列超时兜底**：重连后自动重放未确认消息；同时给「永久排队」设上限与显式失败（Claude Code #91087 反例）。
5. **假连接/静默丢是行业通病**：连微信级产品都要靠「多通道 + 序号 + ack」兜底，单一路径注定有盲区。
6. **状态 UX 三态足够**：发送中 → 成功（回执可选）→ 失败（红❗点击重发）；本项目已实现该 UX，缺的是底层 ack/幂等支撑。

## 2. 调研 B：连接方案备选与自建弱网模拟

### 2.1 连接方案对比（对比维度：第三方依赖 / 稳定性 / 延迟 / 成本 / 自建工作量 / 大陆可达性）

| 方案 | 第三方依赖 | 稳定性 | 延迟 | 成本 | 自建工作量 | 大陆可达性 |
|---|---|---|---|---|---|---|
| **Tailscale（现状）** | 高（Tailscale App/账号/中继 DERP） | 中（假连接、静默断；DERP 中继质量不可控） | 低（直连）/中（DERP 中继） | 免费额度 | 零（已跑通） | 中（DERP 国内不稳定，需自建/选路） |
| **LAN 直连 + mDNS 发现** | 零（同网） | 高（同网） | 极低 | 零 | 低（bridge 绑 LAN 监听 + 广播发现） | 仅局域网，出网不可用 |
| **ZeroTier** | 高（ZeroTier 平台/自建 planet） | 中 | 低/中 | 免费额度 | 低 | 中（同 Tailscale 类） |
| **Cloudflare Tunnel** | 高（CF 平台，域名） | 中高（CF 边缘） | 中（回源绕远） | 免费额度 | 低 | 中（CF 边缘国内波动） |
| **frp 自建中继（VPS）** | 低（自建，仅租 VPS） | 高（自控） | 中（中继一跳） | VPS 月租 | 中（VPS + frps 配置） | 高（自选国内/海外 VPS） |
| **WebRTC（自建信令 + STUN/TURN）** | 低（自建） | 高（P2P，TURN 兜底） | 极低（直连） | TURN 带宽/流量成本 | 高（信令+TURN+移动端 DataChannel 集成） | 高（自建 TURN） |
| **QUIC / HTTP3** | 低 | 中高（连接迁移） | 低 | 低 | 中高（KMP 生态不成熟） | 高 |
| **多通道回退组合** | 中（保留多路） | **最高（多活）** | 低（健康度选最优） | 依组合 | 高（编排复杂度） | 高 |

关键事实与来源：
- frp 官方支持 **xtcp 直连（P2P）与中继 fallback**，即「先打洞、打不通走中继」的开箱方案（[gofrp.org xtcp fallback](https://gofrp.org/zh-cn/docs/features/xtcp/)）。
- WebRTC 的「自建 vs 买」与 NAT 穿透（STUN/TURN）工程实践见 [融云 WebRTC 2026 指南](https://www.rongcloud.cn/blog/webrtc-build-vs-buy-2026-guide) 与 [WorldFoundry NAT 穿透调研](https://raw.githubusercontent.com/wbniv/WorldFoundry/refs/heads/2026-new-level/docs/investigations/2026-05-26-internet-voice-video-nat-traversal.md)。
- Tailscale vs ZeroTier 对比（延迟/成本/自建 headscale）见 [speedtesthq](https://speedtesthq.com/compare/tailscale-vs-zerotier) 与 [ZeroTier 致命 bug → 切 Tailscale/headscale 实践](https://blog.csdn.net/qq_40999403/article/details/154946506)。
- 内网穿透方案横向（frp/Tailscale/ZeroTier/CF Tunnel/自建）见 [五款内网穿透工具评测](https://cloud.baidu.com/article/3797559) 与 [常用内网穿透盘点](https://post.smzdm.com/p/a3xnmop7/)。
- QUIC/HTTP3 的**连接迁移**（WiFi↔4G 切网 IP 变、连接不断）是相对 TCP/WS 的独有优势（[HTTP3/QUIC 弱网抗抖动](https://my.oschina.net/emacs_7985529/blog/19466333)、[HTTP1.1/2/3 连接迁移解析](https://blog.csdn.net/wxdzuishaui/article/details/151857355)）。

**推荐组合（理由）**：
1. **LAN 直连优先**（bridge 侧新增 LAN 监听 + mDNS 广播）：同网时零第三方、最低延迟，直接消掉「在家还依赖 Tailscale」这一最大不稳定源。
2. **自建 frp 中继兜底**（VPS）：出网/跨网时走自建中继，彻底摆脱 Tailscale 第三方依赖，大陆可达性自控。
3. **Tailscale 保留为「第三路」而非主路**：作为过渡期兼容（现有用户已配好），新三路健康度评分自动切换，跑稳后可选下线 Tailscale。
4. **WebRTC/QUIC 列为长期演进**：KMP 生态与自建 TURN 成本当前不划算，不急于引入。

> 说明：LAN 直连在现状架构下「不可行」是因为 dsh 只绑 127.0.0.1（`docs/connection-architecture.md` §7.2）。解法是 **bridge 自建一个绑定 LAN 接口的二级 WS 监听**（复用同一鉴权/协议 handler，等价于内置 `tailscale serve` 的端口转发），而非要求 dsh 内核放开回环绑定。安全面从「回环终结」变为「LAN 监听 + 同款 Bearer/配对鉴权」，需要用户拍板（见 §4）。

### 2.2 自建可控网络条件模拟器方案盘点（好/中/差 = 带宽/延迟/丢包/抖动可调）

| 方案 | 形态 | 可控粒度 | 是否需 root/特权 | 接入测试流成本 | 适用 |
|---|---|---|---|---|---|

| **toxiproxy / comcast / speedbump** | 独立 TCP 代理（延迟/丢包/超时/限速），带 API | 连接级全可控，可编程 | 无需 root | 低（有 HTTP 控制接口） | 通用故障注入（[speedbump](https://news.ycombinator.com/item?id=39012697)、[Network Tools](https://devops-daily.com/posts/network-tools-that-simulate-slow-network-connection)） |

**落地建议（自建组件形态 + 控制接口 + 接入现有测试流）**：

1. **主形态：扩展 `tools/mock-bridge` 为「可配置弱网假服务端」**。
   - 在现有 WS server 的 `send`/`on message` 路径插入可配置「弱网管道」：对**每个下行帧**注入随机/固定延迟、按概率丢包、限速（token bucket）、抖动（延迟方差）。
   - 控制接口沿用其现有 HTTP 端点风格，新增：
     - `POST /remote/net-condition` `{profile: "好"|"中"|"差"}` 或 `{latencyMs, jitterMs, lossRate, bandwidthBps}`
     - `GET /remote/net-condition` 读当前配置；`POST /remote/net-condition/random` 随机翻转（模拟闪断）。
   - 预设三档：好（0 丢包 / <20ms）、中（2% 丢包 / 80ms±30ms / 512KBps）、差（8% 丢包 / 300ms±100ms / 128KBps）。
   - 接入现有测试流：手机 `connectDevice(mock-bridge)` → 调 `net-condition` 切档 → 发消息 → 断言「发送中→失败→自动重发→回显去重」全链路。与真机自测（`startup-smoke-test` + uiautomator）串联。

2. **辅形态：桥前自建 TCP 弱网代理**（toxiproxy/speedbump 或 ~30 行 Node 代理）：插在「手机 → mock-bridge/真实 bridge」之间，对**真实 bridge** 做传输层弱网（不动业务代码），覆盖「真实桌面端 + 弱网」场景。

3. **系统级仅作兜底**：macOS Network Link Conditioner / pf+dummynet 用于「整体弱网」的手测；Android tc/netem 用于有 root 真机的端到端复现。三者不互斥，按「确定性可重复（mock 弱网）> 传输层（代理）> 系统级（手测）」的优先级取用。

> 关键原则：**弱网必须可编程、可复现**（固定种子/固定丢包序列），否则无法做「消息发送鲁棒性」的回归断言；GUI 类（Network Link Conditioner）只能辅助手测。

## 3. 调研 C：对本 App 的方案权衡（核心交付）

### 3.1 现状缺口 → 改造靶点（对照 §0）

| 靶点 | 现状 | 目标 |
|---|---|---|
| T1 假连接判活 | 仅协议层 30s PING，无应用层 ping/pong，~50s 才判死 | 双向应用层心跳 + pong 超时判死（秒级） |
| T2 假送达 | `send()` 返回 true ≠ 服务端已处理 | 服务端 `send_message` 回 `ack{msgId}`，客户端以 ack 为准 |
| T3 无幂等/序号 | 回显去重用「文本+60s」模糊匹配，重发会重复投递 | `send_message` 增 `msgId`；服务端按 msgId 幂等去重；回显匹配改 msgId |
| T4 无持久化队列 | pending 纯内存，杀进程即丢 | 本地落盘队列（发送前落盘、ack 后删），冷启动恢复 |
| T5 无断线自动重发 | 仅手动点❗重发 | 重连成功后自动重放未 ack 消息（带上限） |
| T6 连接单点（Tailscale） | 唯一无线路径 | 多通道回退（LAN 优先 + frp 中继 + Tailscale 保留） |

### 3.2 四个组合方案

> 每个方案都**共享同一套消息可靠性底座**（T1~T5），差异在**连接层**（T6）走多远。

**方案 A：保持 Tailscale + 补消息可靠性底座（最小改动）**
- 连接层不变（Tailscale + 多候选退避 + WS）；只做 T1~T5。
- 优点：改动小、不引入新基础设施、Tailscale 已跑通；把 P0 的「消息必达」先落地。
- 缺点：**痛点①（第三方 Tailscale 不稳定）不根治**；假连接只能靠「更快的判活 + ack + 重发」缓解，隧道本身断/中继质量仍不可控；大陆/公司网可达性仍受限。
- 成本：低 ｜ 复杂度：低 ｜ 可靠性上限：**中**（受隧道质量封顶）。

**方案 B：LAN 直连优先 + frp 自建中继回退 + 消息底座（去第三方依赖）**
- bridge 新增 LAN 监听 + mDNS 广播；外网走自建 frp 中继（VPS）；Tailscale 逐步下线。叠加 T1~T5。
- 优点：**彻底摆脱第三方 Tailscale**（痛点①根治）；大陆可达性自控（自选 VPS）；LAN 路径零第三方、最低延迟。
- 缺点：需一台 VPS（月租 + 运维）；frp 中继是单点（需考虑高可用/心跳）；mDNS 在部分路由器不可靠（需广播 + 手动 IP 双通道）；自建工作量中等。
- 成本：中 ｜ 复杂度：中 ｜ 可靠性上限：**高**。

**方案 C：全自建（frp/WebRTC）+ 消息底座 + ack（最彻底）**
- WebRTC DataChannel（自建信令 + STUN/TURN）为主、frp 兜底，未来演进 QUIC/HTTP3；叠加 T1~T5。
- 优点：P2P 直连最低延迟、无固定带宽成本；QUIC 连接迁移是移动切网最优解。
- 缺点：信令/TURN 自建复杂；KMP 侧 WebRTC/QUIC 生态不成熟、调试成本高；**远超当前需求**（一对一控制面，非音视频）。
- 成本：高 ｜ 复杂度：高 ｜ 可靠性上限：最高但性价比最低。

**方案 D：多通道回退组合（Tailscale + LAN + frp 三路健康度评分自动切换）+ 消息底座（推荐折中）**
- 客户端维护「候选通道 = {LAN, Tailscale, frp}」，按「连通性/延迟/丢包」健康度评分实时选路与无缝切换；消息层统一 T1~T5。
- 优点：每路多活，单路故障无缝切换，可靠性上限最高；**渐进演进**（先加 LAN，再加 frp，再视情况下线 Tailscale），不用一次押注。
- 缺点：客户端连接编排复杂度最高（多连接/健康度/切换竞态）；前期工作量最大。
- 成本：中高 ｜ 复杂度：高 ｜ 可靠性上限：**最高**。

### 3.3 推荐方案与分阶段路线

**推荐：以方案 A 的「消息可靠性底座」为第一优先（P0 共性前置），向方案 D 的多通道渐进演进**。理由：
- 消息可靠性底座（T1~T5）是 A/B/C/D **共同前置**，且直接命中 P0 痛点②，先做收益最大、无选型风险。
- 连接层去 Tailscale（痛点①）是「体验级」改善，但涉及新增基础设施（LAN 监听安全面 + VPS），需用户拍板后分阶段做，不宜一次押注全自建。

**分阶段路线**：

- **阶段 1（P0，先做）——消息必达底座**：T2+T3 协议升级（`send_message` 增 `msgId`，服务端回 `ack{msgId}` + 幂等去重 + 回显改 msgId 匹配）→ T4 本地持久化队列（发送前落盘、ack 后删、冷启动恢复）→ T5 重连自动重放（带重试上限 + 显式失败）→ T1 应用层心跳判活（双向 ping/pong，秒级判死）。
- **阶段 2（P1）——LAN 直连优先**：bridge 新增 LAN 监听（复用鉴权）+ mDNS 广播发现；客户端候选通道加 LAN 并置顶。弱化对 Tailscale 的依赖（在家场景根治痛点①）。
- **阶段 3（P1，待拍板）——frp 自建中继兜底**：若用户决定摆脱 Tailscale，则租 VPS 自建 frp，作为出网回退；三路健康度评分切换（方案 D 收敛）。
- **阶段 4（P2，长期）——弱网模拟器**：扩展 `tools/mock-bridge` 为可配置弱网桩（§2.2 主形态），把消息鲁棒性做成可重复回归；WebRTC/QUIC 作为远期演进观察项，不主动立项。

### 3.4 与在途《消息发送鲁棒性设计》的协调

- 本调研只定「**要不要 ack/幂等/持久化/多通道**」的**方向与边界**；《消息发送鲁棒性设计》负责**字段级协议（msgId 生成规则、ack 超时、退避、落盘格式、队列容量上限、去重窗口）**。
- 交叉引用：本报告 T1~T6 是设计文档的输入约束；设计文档落地后本报告「待拍板清单」里对应的项即告闭环。

## 4. 待拍板清单（重大选型，铁律 1）

> 以下每项均需用户拍板后才进入实施；序号即优先级。

1. **消息可靠性协议升级（ack + msgId + 幂等）**：是否同意 `send_message` 增 `msgId`、服务端回 `ack{msgId}` 并做幂等去重？（协议设计方向变更，影响 App + bridge 两端协议镜像与回显去重逻辑）
2. **本地消息持久化选型**：客户端 pending 队列落盘方案——SQLite（结构化/事务/排序）vs 文件/DataStore（轻量）vs 两者分层？（铁律 1 持久化方案需拍板）
3. **断线自动重发策略边界**：重连后自动重放未 ack 消息的**重试上限 / 超时 / 何时转「显式失败红❗」**？（涉及「自动重发可能重复投递」的语义，用户需认可 at-least-once 语义）
4. **假连接判活收紧**：是否引入**应用层双向 ping/pong + pong 超时判死**（替换/叠加现有 30s 协议心跳），把判死从 ~50s 压到秒级？
5. **LAN 直连的安全面变化**：是否同意 bridge 新增**绑定 LAN 接口的二级 WS 监听**（复用鉴权，等价内置端口转发）+ mDNS 广播发现？（从「回环终结」扩大到「LAN 监听」，安全面变化需拍板）
6. **是否自建 WAN 中继（frp/VPS）**：为根治 Tailscale 第三方依赖，是否租 VPS 自建 frp 中继作为出网回退？（成本/运维 vs 依赖/可达性）；还是继续保留 Tailscale 作为外网路径？
7. **弱网模拟器形态**：采用「扩展 mock-bridge 注入弱网（推荐主形态）+ 桥前 TCP 代理（辅）+ 系统级（手测兜底）」三件套，还是只要其一？
8. **多通道演进节奏**：是否接受「阶段 1 先做消息底座 → 阶段 2 LAN 直连 → 阶段 3 frp 中继 → 阶段 4 弱网模拟」的渐进顺序？（决定资源投入时点）
