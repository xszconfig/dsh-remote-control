### 已拍板细则（2026-09-10，方案② + ⑤）

1. **启动条件**：只要检测到主代理（顶层会话 `status=running`）或任意子代理（`parentSessionId != null` 且 `status=running`）在运行，就启动前台服务。
2. **通知内容**：展示「N 个主代理 · M 个子代理正在运行」，数量随服务端投影实时更新（铁律 6：counts 以 `SessionUiState.sessions` 的 status 为准，客户端不推算）。
3. **结束条件**：主代理和子代理都结束后（counts=0），停止前台服务并取消通知。
4. 通知展示期间前台服务持续保活；点击通知打开 app。
5. **FGS 类型 = `connectedDevice`**（targetSdk 35：`dataSync` 有 6h 上限会 `RemoteServiceException`，`connectedDevice` 无上限）；manifest 加 `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` + `CHANGE_NETWORK_STATE` 权限与 `android:foregroundServiceType="connectedDevice"`。
6. **Android 12 后台启动限制**：FGS 启动/更新通知在 App 前台观察到 counts 变化时执行；设计上保证 counts>0 时服务持续存在。
7. **断连边缘**：WS 断开时用最后已知 counts 维持 FGS，重连后按服务端投影校正（含 counts 归零→停服务取消通知）。
8. **通知渠道**：低打扰级别（不响铃不震动，与既有通知渠道风格一致）。
9. **⑤ 白名单引导（同批做）**：SettingsScreen 加「后台保活」小节——说明华为 EMUI 需把应用设为「手动管理」（应用启动管理）+ 电池优化豁免，提供「申请忽略电池优化」按钮（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）。

## 一、需求背景

- **现象（2026-09-09 真机验收，功能级问题）**：App 退后台（按 HOME）后应用层 ping/pong 停止、服务端 `/remote/connected` 变空，前台化才自动重连。
- **影响（P0）**：主动通知里的**结果交付（D1/D2/D3）**依赖手机实时收到 agent idle 事件（`agent_status` running→idle / `turn_status` close / `goal_update` 终态）。长时间后台时 WS 断开，这些事件到不了手机 → **结果交付通知漏发**。本次验收是趁短暂后台（连接尚未被系统回收）才触发成功的。
- **事实边界**：
  - 真机 = 华为 HBN-AL00 / Android 12（API 31）/ EMUI（后台管理激进，PowerGenie 会杀后台进程）。
  - 服务端 = 用户自托管（本机 Mac 上的 DSH + bridge），**无云推送通道**（无 FCM/厂商推送），Tailscale 组网。
  - App 已有：`ConnectionManager` 应用层 ping/pong（20s/10s）+ 断线自动重连 + `PendingStore` 消息队列持久化；通知 = 本地通知（`NotificationController`/`NotificationHandoff`），夜间勿扰 22–08 静默结果交付。
- **核心矛盾**：手机是「通知接收端」，但没有可用的「进程被系统挂起/杀死后仍能唤醒」的通道（FCM/厂商 Push）。这决定了本问题的答案只能从「让进程尽量别死」+「死了之后补」两个方向找，且两个方向在华为真机上都有已知硬伤（见 §五/§六）。

## 二、核心需求点拆解

1. **N1 结果交付不永久丢失**：D1/D2/D3 通知在长时间后台（1h / 整夜）后仍能被送达（至少是「用户回前台后补发」，不静默丢）。
2. **N2 缩小漏发窗口**：在「有 running goal/会话」这一高价值窗口内，尽量保持连接存活，让通知接近实时（目标 ≤ 分钟级，而非小时级）。
3. **N3 省电与低打扰**：不以「常驻通知图标 + 整夜耗电」为代价换取保活（移动端体验红线）。
4. **N4 华为 EMUI 可落地**：方案必须在华为真机（PowerGenie 激进杀后台）上真实有效，不能只在原生 Android 上成立。
5. **N5 平台合规**：targetSdk 35 下前台服务类型声明/权限/超时限制必须合法（Android 14/15 硬约束）。
6. **N6 复用现有机制**：与现有「服务端投影（铁律 6）」、`会话×轮次` 通知幂等键、hello 补发、`PendingStore` 落盘能力配合，不另起炉灶。

## 三、核心指标拆解

| 指标 | 口径 | 达标 | 测量方法 |
| --- | --- | --- | --- |
| 后台 1h 送达率 | 退后台后 1h 内 agent idle → 通知在手机上出现 | ≥ 90%（配合按需 FGS + 白名单） | 真机：mock-bridge 或真实 bridge 造 idle 事件，`adb shell dumpsys notification` 查通知 |
| 整夜漏发恢复 | 整夜断连后，次日回前台能否补发漏掉的 D1/D2/D3 | 100%（事件不丢） | 服务端台账 + 重连拉取补投，客户端断言通知幂等去重 |
| 常驻打扰 | 空闲态是否显示常驻通知 / 增加耗电 | 空闲态无常驻通知 | 空闲态 `dumpsys notification` 无本包常驻 FGS 通知 |
| 平台合规 | targetSdk 35 FGS 类型/权限/超时声明 | 0 崩溃、无 `RemoteServiceException` | Android 15 模拟器跑 6h+ 边界 + `lint`/`detekt` |
| 华为可落地 | 引导后前台服务在华为 EMUI 存活 | 引导一次后 ≥ 可复现存活 | 真机 HBN-AL00：应用启动管理手动三开 + 电池豁免后压测 |

## 四、预期收益

- **用户**：结果交付通知不再静默漏发（核心痛点）；「跑一个长任务后去忙别的，回来看结果」这一核心场景闭环。
- **开发**：把「通知必达」从「依赖进程存活」的脆弱假设，改到「服务端投影 + 重连补投」的确定性机制上（与铁律 6 一致），可测试、可回归。
- **稳定性**：消掉「结果交付依赖客户端内存态幂等键 + 实时事件」这一单点脆弱性。

## 五、技术方案设计

### 5.0 现有机制基线（代码实证）

- **连接层**：`ConnectionManager`（`composeApp/src/commonMain/.../ConnectionManager.kt`）应用层 ping/pong（`PING_INTERVAL_MS=20s`/`PONG_TIMEOUT_MS=10s`）+ 断线自动重连；后台时进程被挂起 → 该循环停止，WS 断开。
- **通知幂等键**：`NotificationController.kt:143` `notifiedKeys` 为**纯内存 `mutableSetOf`**——进程被杀/重启即清空；键格式 `delivery:{sessionId}:{turnKey}`（`会话×轮次`）。
- **hello 补发现状**：`BridgeClient.kt:1286-1293` 重连后只按服务端快照补发**审批/提问**（可从快照推导）；**结果交付不补发**——因为「idle 过」是瞬时事件，无法从 hello 快照推导（`BridgeClient.kt:1421-1433` D1/D2、`1510-1524` D2、`1447-1454` D3 都是实时事件驱动）。
- **无任何前台服务**：`AndroidManifest.xml` 无 `<service>`、无 `FOREGROUND_SERVICE*` 权限；`targetSdk=35, minSdk=26`（`gradle/libs.versions.toml`）。

### 5.1 五个候选方案（含互补项）

**方案① 常驻前台服务保活（dataSync/connectedDevice 类型 + 常驻通知）**
- App 启动即拉起前台服务，保持 WS 长连 + 常驻通知图标。
- 关键点：Android 14+ 必须声明 `foregroundServiceType` + 对应 `FOREGROUND_SERVICE_<TYPE>` 权限（普通权限，无运行时弹窗）；**类型选型直接影响是否踩 6h 上限**（见 §六）。

**方案② 按需前台服务（仅存在 running goal/会话时启动）**
- 仅当存在 running goal 或 running 会话时启动前台服务；最后一个 running 结束（即 D1/D2/D3 已触发）后停止。
- 空闲态不保活（省电、无常驻通知）；「有活」窗口内 WS 保持在线，缩小漏发窗口。

**方案③ 服务端投影兜底（不保活，重连补投递）**
- bridge 记录「待投递通知台账」（`会话×轮次` 幂等键 + 事件载荷），手机重连后拉取补发。
- 漏发窗口 = 断连期间；长后台后**打开 App 才能收到**（不解决「后台实时」，但解决「永久丢失」）。

**方案④ 接受现状（文档化限制）**
- 明确文档化「长后台结果交付通知可能漏，等用户回前台」，不引入任何机制。

**方案⑤ 华为白名单 UX 引导（纯引导，互补项）**
- 一次性引导用户：应用启动管理→手动管理→三项全开（自启动/关联启动/后台活动）；电池优化→「不允许」（豁免）；受保护应用/「保持屏幕关闭后运行」。
- 是②（乃至①）在华为真机能否生效的**必要前提**，本身不保活但让保活可行。

### 6.1 华为 EMUI 硬伤（务必显著标注）

> ⚠️ **结论：前台服务在华为 EMUI 不是银弹。** 社区权威站 dontkillmyapp.com 给华为打 **5 💩（最差）**，明确记载：
> - EMUI 9+（Android P+）内置任务杀手 **PowerGenie**，「kills everything not whitelisted by Huawei and does not give users any configuration options」——杀掉一切不在华为白名单的进程（**含前台服务**），且**无法手动把自定义 App 加进其白名单**，唯一办法是 `adb shell pm uninstall -k --user 0 com.huawei.powergenie`（XDA 记载）。
> - 早期 EMUI 的 `HwPFWService` 会「force stop abnormal wakelock app」，后台处理超过 ~60 分钟即被杀。
> - **含义**：①/② 若不加⑤（用户侧白名单），在华为真机上仍会被 PowerGenie 杀掉 → 保活失效、通知照漏。因此 **⑤ 不是可选项，而是①/② 在华为真机上的必要配套**；③ 则完全不受此影响。

### 6.2 前台服务类型选型硬伤（务必显著标注）

> ⚠️ **结论：若走 FGS 路线，必须用 `connectedDevice` 或 `specialUse`，禁用 `dataSync`。** 依据（Android 官方）：
> - **`dataSync` 有 6h/24h 硬上限（Android 15 / targetSdk 35）**：官方《前台服务超时》原文——「系统允许 dataSync 和 mediaProcessing 前台服务在 24 小时内总共运行 6 小时，之后系统会调用 `Service.onTimeout(int, int)`」；几秒内不 `stopSelf()` 则抛 `RemoteServiceException: "A foreground service of type [service type] did not stop within its timeout"`。**整夜（~8–10h）必然超时崩溃**，直接违背 N2/N4。
> - **`connectedDevice` 无 6h 上限，语义正合适**：官方定义「与需要蓝牙、NFC、IR、USB **或网络连接**的外部设备进行互动」——正是「保持与桌面的网络连接」；权限 `FOREGROUND_SERVICE_CONNECTED_DEVICE`，运行时前提只需声明 `CHANGE_NETWORK_STATE`（或 `CHANGE_WIFI_STATE`/`CHANGE_WIFI_MULTICAST_STATE` 等**普通权限**，无运行时弹窗）即可满足。
> - **`specialUse` 为兜底**：无运行时前提，但须在 `<service>` 内声明 `<property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="..."/>` 说明用途；Play 上架需向审核说明（本项目自托管/内部使用，不受 Play 约束，但语义不如 connectedDevice 诚实）。
> - **注**：当前真机 Android 12（API 31）不触发 6h 上限（该行为属 Android 15 / targetSdk 35）；但 App targetSdk=35，须对 Android 15+ 设备正确。

## 七、最终选择与决策逻辑

### 推荐：**③（服务端投影补投递）为可靠性底座 + ②（按需前台服务）为「有活时尽量在线」尽力层 + ⑤（华为白名单引导）为②生效的必要配套**

- **③ 是「不丢」的确定性保证，优先级最高**：它是五个方案里唯一「不依赖手机进程存活」的兜底，直接命中 P0（结果交付永久丢失）；且与铁律 6（服务端投影为准）、现有 `会话×轮次` 幂等键、hello 补发模式天然契合。实现成本主要在 bridge 端加「待投递通知台账 + 拉取接口」，App 端复用现有 hello 补发逻辑 + 把内存幂等键持久化（`PendingStore` 同款「临时文件 + rename」落盘）。代价：漏发窗口 = 断连期间（长后台后**回前台才补**），不解决「后台实时」。
- **② 用于缩小漏发窗口，而非保证不丢**：在「存在 running goal/会话」这一最高价值窗口（正是 D1/D2/D3 会触发的时刻）内保活 WS，把「后台 1h」场景的实时性从「漏」拉到「接近实时」；空闲态不保活，满足 N3（省电、无常驻通知）。类型用 **`connectedDevice`**（声明 `CHANGE_NETWORK_STATE` 普通权限），规避 dataSync 6h 硬伤。
- **⑤ 是②在华为真机生效的唯一路径**：PowerGenie 会杀前台服务，② 若不加⑤在华为形同虚设；⑤ 成本极低（一次性引导弹层/跳设置页），对③也有收益（缩短断连窗口）。
- **不选①**：常驻通知 + 整夜耗电违反 N3；且华为仍被杀（不配合⑤不生效，配合⑤则②在「有活」窗口已足够，① 的「空闲也保活」纯属浪费）。
- **④ 仅作过渡底线**：在③实施落地前，作为「诚实文档化」的兜底；不作为最终方案。

### 为什么不是其它组合

| 备选 | 被否原因 |
| --- | --- |
| 仅① | 常驻打扰 + 华为 PowerGenie 仍杀 → 花成本却不可靠（§6.1） |
| 仅② | 空闲窗口（恰恰是「无 running、但历史结果刚交付」时）通知仍漏；且华为不引导不生效 |
| 仅③ | 后台 1h 内无法实时（回前台才补），N2 不达标 |
| ③+⑤（无②） | 华为上回前台补投可保证不丢，但「后台 1h 实时」仍缺；② 成本不高、收益明确 |
| ①+③+⑤ | 比「②+③+⑤」多出「空闲也保活」的耗电/通知成本，无额外收益 |

## 八、对现有架构的影响

### 改动面

- **App 端**：
  - （②）新增前台服务（`connectedDevice` 类型）+ `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_CONNECTED_DEVICE`、`CHANGE_NETWORK_STATE` 权限声明；由 running goal/会话状态（`AgentStatus`/`TurnStatus`/`GoalUpdate`）驱动启停。
  - （③）把 `NotificationController.notifiedKeys` 从内存改为持久化（复用 `PendingStore` 落盘机制），支撑「重连补投 + 幂等去重」；新增「拉取待投递通知」调用与补发入口（复用 `handleHello` 现有补发段落）。
  - （⑤）一次性白名单引导 UI（复用现有 `NotificationHandoff` 的「权限引导」交互范式）。
- **bridge 端**：
  - （③）新增「待投递通知台账」：记录 `会话×轮次`（turnKey / goal-updatedAt）幂等键 + 通知载荷 + 客户端已确认游标；新增拉取接口（对齐现有 hello 快照风格）。

### 风险点

1. （③）**幂等键语义**：`会话×轮次` 的 `turnKey` 目前是客户端侧 `turnStartBySession` 推导，补投需服务端权威生成同一 `turnKey`，否则补投与实时投递去重失效（重复通知）→ 需把轮次 key 上移到服务端（与铁律 6 一致）。
2. （③）**补投时序**：补投在 hello 之后、门控（前台浏览该会话）判定之前执行，避免「用户正在看该会话仍弹通知」——复用现有 `decideAndPost` 的未发即回退幂等位逻辑（`NotificationController.kt:150-154`）。
3. （②）**启停竞态**：running 状态突变（goal 在 idle 瞬间又起新轮）需防「停止后又立刻启动」抖动（加启停延迟/状态机）。
4. （②+⑤）**华为仍可能杀**：即便白名单，极端场景（低电、省电模式）仍可能回收，故②永远只是「尽力」，③ 才是「保证」。

### 兼容性与回滚

- ②⑤ 为增量，回滚 = 移除 FGS 声明与引导，无协议影响。
- ③ 涉及 bridge 协议扩展（新增事件/接口），需**向后兼容**（旧 App 不调新接口无影响；新 App 对旧 bridge 降级为「无台账，走④行为」）。

## 九、后续迭代规划

1. **P0（先做）③ 服务端投影补投递**：bridge 通知台账 + 拉取接口；App 端幂等键持久化 + 重连补发。这是「不漏」的地基。
2. **P1 ② 按需前台服务**：`connectedDevice` 类型 + running 驱动启停 + 状态机防抖。
3. **P1 ⑤ 华为白名单引导**：一次性引导（自启动/关联启动/后台活动三项 + 电池优化豁免）。
4. **P2 真机压测**：HBN-AL00 上「后台 1h / 整夜」两档送达率 + 通知幂等去重回归（mock-bridge 造 idle 事件，`dumpsys notification` 断言）。
5. **触发再评估**：若未来接入 FCM/厂商 Push（有云推送通道），③④ 可整体替换为「Push 直投 + 服务端离线队列」；在无云通道前，③ 是唯一确定性兜底。
