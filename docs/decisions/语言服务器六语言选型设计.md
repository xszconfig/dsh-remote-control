## 一、需求背景

- **为什么做**：bridge 作为手机远程控制的后端，需要为 Agent 编辑/写入的源文件提供**实时代码诊断**（类型错误、未解析引用等），并广播到手机端展示，帮助用户远程定位代码问题。
- **边界**：v1 只做**诊断**，不做补全/悬停/跳转（后经 lsp_query 工具扩展了 hover/definition/references 查询）；按语言**懒启动**语言服务器（stdio + Content-Length 帧）；二进制缺失时优雅降级（记一次日志，不重试风暴）；每语言一个 server 实例 + 一个 workspace root。

## 二、核心需求点拆解

1. **六语言诊断覆盖**：TypeScript / JavaScript / Python / Rust / C·C++ / Kotlin。
2. **懒启动 + 优雅降级**：文件首次变更时拉起对应 server；二进制缺失时该语言自动禁用。
3. **诊断实时回调**：`publishDiagnostics`（push）或 `textDocument/diagnostic`（pull）→ `onDiagnostics` 回调 → 广播到手机（按会话隔离）。
4. **stdio LSP 统一适配**：所有语言共用一套 Content-Length 帧解析 + 请求/通知封装。
5. **项目上下文**：Kotlin 需项目根 + buildTools 导入才能出语义诊断（其余语言靠各自 workspace 感知）。

## 三、核心指标拆解

| 指标 | 口径 | 现状 |
| --- | --- | --- |
| 语言覆盖 | LANGS 表语言数 | 6（TS/JS 共用 typescript-language-server） |
| 诊断模式 | push / pull | 仅 Kotlin 用 pull（`diagnosticProvider`），其余 push |
| 启动成本 | 冷启动到首次诊断 | Kotlin 最重（JVM 30-60s + 项目导入数分钟），其余秒级 |
| 体积 | 二进制/依赖大小 | Kotlin 约 1.1GB（自包含 JBR），其余为系统级轻量二进制 |
| 二进制缺失降级 | 找不到时行为 | 记日志 + 标记 missing，不重试风暴 |

## 四、预期收益

- **对用户**：编辑六种语言源文件时，类型错误/未解析引用实时上屏到手机，远程即可定位问题。
- **对开发效率**：Agent 写代码后立即得到语义反馈，减少往返。
- **对可维护性**：统一 stdio LSP 抽象，新增语言只需在 LANGS 表加一行 + 按需加 per-language 分支。

## 五、技术方案设计

### 5.1 总体架构

```
Agent 写入文件 notifyFileChanged(path)
  → langFor(扩展名) → ensureServer(lang, path)
    → findExecutable(cmd[0]) → spawn(bin, args, stdio=pipe)
    → initialize(processId/rootUri/capabilities/初始化参数)
    → initialized → didOpen(全文) → 400ms 节流 didChange(全文)
  → 诊断来源：
      push：textDocument/publishDiagnostics → onDiagnostics
      pull（仅 Kotlin）：textDocument/diagnostic 请求 → onDiagnostics
  → onDiagnostics(path, sessionId, diags) → 广播手机
```

### 5.2 六语言命令（LANGS 表）

| 语言 | languageId | 扩展名 | 命令 |
| --- | --- | --- | --- |
| TypeScript | typescript | .ts/.tsx/.mts/.cts | `typescript-language-server --stdio` |
| JavaScript | javascript | .js/.jsx/.mjs/.cjs | `typescript-language-server --stdio` |
| Python | python | .py | `pyright-langserver --stdio` |
| Rust | rust | .rs | `rust-analyzer` |
| C/C++ | cpp | .c/.h/.cc/.cpp/.hpp | `clangd` |
| Kotlin | kotlin | .kt/.kts | `kotlin-lsp --stdio --system-path <index>`（二进制三级解析） |

### 5.3 关键差异点

- **Kotlin 是唯一 pull 诊断 + 项目导入**：官方 IntelliJ 内核用 `diagnosticProvider`（pull），且必须 `buildTools`（gradle/maven）+ 项目根 realpath 导入出 content root，否则 `KotlinProblemHighlightFilter` 判 `not-under-content-root` → 0 诊断。其余五语言都是 push `publishDiagnostics`，无 buildTools 概念。
- **typescript-language-server 需显式指路 tsserver**：它不捆绑 TypeScript，bridge 用 `tsserverPath()` 定位全局 `tsserver.js`。
- **clangd 需编译数据库**：`compile_commands.json`（由构建系统生成），缺失时诊断退化为语法级。

## 六、多方案优劣势对比

### 6.1 TypeScript / JavaScript

| 维度 | typescript-language-server（选用） | 备选：vtsls / Volar / deno lsp |
| --- | --- | --- |
| 内核 | tsserver（TS 官方语言服务），语义最准 | vtsls 更快但新；Volar 面向 Vue；deno 面向 Deno 运行时 |
| 维护 | 社区活跃（tsserver 官方驱动） | 各自活跃 |
| 依赖 | Node + 需显式指路 tsserver.js | 各有依赖 |
| 选择理由 | 语义准确、生态默认、与 tsserver 能力对齐 | 无强迁移动机 |

### 6.2 Python

| 维度 | pyright（选用） | 备选：pylsp / jedi / ruff-lsp |
| --- | --- | --- |
| 内核 | 微软静态类型检查器，自包含无第三方依赖 | pylsp 需 jedi+rope 组合；ruff 只管 lint 不管类型 |
| 速度 | 快（增量） | pylsp 较慢 |
| 选择理由 | 类型诊断准 + 安装简单（单 `pyright-langserver` 二进制） | pylsp 组合复杂、ruff 不覆盖类型诊断 |

### 6.3 Rust

| 维度 | rust-analyzer（选用） | 备选：rls |
| --- | --- | --- |
| 内核 | rust-lang 官方，事实标准 | rls 已废弃（官方退役） |
| 选择理由 | 唯一活跃、语义最全（cargo 项目感知） | 无备选价值 |

### 6.4 C/C++

| 维度 | clangd（选用） | 备选：ccls / cpptools |
| --- | --- | --- |
| 内核 | LLVM 官方，基于 clang 语义 | ccls 类似但维护弱；cpptools 微软 VSCode 专用 |
| 选择理由 | 语义准、LLVM 官方维护 | ccls 停更、cpptools 绑定 VSCode |

### 6.5 Kotlin

| 维度 | 官方 kotlin-lsp（选用） | 备选：fwcd / Rust 实现 |
| --- | --- | --- |
| 内核 | IntelliJ 内核（语义最强） | fwcd=kotlin-compiler 但 deprecated；Rust=tree-sitter 语法级无类型检查 |
| 详见 | 完整论证见 `docs/decisions/KotlinLSP选型论证.md` | — |

## 七、最终选择与决策逻辑

- **TS/JS**：`typescript-language-server`（tsserver 内核）——语义最准、生态默认；代价是需显式定位 `tsserver.js`（bridge 已处理）。
- **Python**：`pyright`（微软）——类型诊断准、单二进制自包含、无 pylsp 的插件组合复杂度。
- **Rust**：`rust-analyzer`（rust-lang 官方）——唯一活跃、cargo 感知。
- **C/C++**：`clangd`（LLVM 官方）——clang 语义最准、维护健康。
- **Kotlin**：官方 JetBrains kotlin-lsp——语义最强 + KMP 方向正确（用户 2026-09-06 拍板维持官方等 LSP-1561 修复，见 Kotlin 选型文档）。

**决策逻辑**：每语言都选「语义最准 + 官方/生态默认 + 维护健康」的实现，而非追求极致的轻量或速度；唯一例外是 Kotlin——官方因 Android CCE 暂有假阴性，但仍是方向正确 + 修复在路上的最优解。

## 八、对现有架构的影响

- **改动面**：全部落在 bridge `src/lsp.ts`（`LANGS` 表 + `ensureServer`/`syncDoc`/`handleMessage`/per-language 分支），不涉及协议层/上层广播。
- **风险点**：Kotlin 的 EAP 过期（需定期升级）与 Android CCE 假阴性；clangd 缺 `compile_commands.json` 时诊断降级。
- **兼容性/回滚**：每语言独立懒启动，单语言二进制缺失只影响该语言；Kotlin 旧二进制已备份可回滚。

## 九、后续迭代规划

- **Kotlin 升级路径**：盯 JetBrains 发布含 LSP-1561 修复（commit `4be8d16815ea`）的构建（`263.4xxx+` 或 `264.x`），按 `~/.dsh/kotlin-lsp/UPGRADE-NOTES.md` 升级并复测 CCE 消失；官方出稳定版则优先切稳定版。
- **新增语言评估**：候选 Go（gopls）、Java（jdtls，但 Kotlin LSP 已带 Java 能力）、Swift（sourcekit-lsp）、Shell 等——**新增语言属于技术选型，须先对比论证后请用户拍板**（铁律 1），不擅自加。
- **诊断模式统一**：若后续新增 pull 诊断语言，可复用 Kotlin 的 `pullDiagnostics` + `intellij/ready-for-test` 重拉机制。
