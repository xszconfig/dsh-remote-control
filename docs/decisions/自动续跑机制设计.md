## 一、需求背景

**为什么做这件事：**

DSH 的 Agent 会话跑的是「长任务」——一次转盘任务可能持续数十分钟到数小时（跨多个 model turn、多次工具调用、多轮子代理）。当 DSH 服务端因升级/重启/崩溃而中断时，主会话正在进行的工作会**原地丢失**：用户（手机端）无法知道「刚才做到哪一步、下一步该做什么」，Agent 也不会自动续上，只能靠用户重新描述一遍上下文。

- **用户诉求**：服务重启后，手机端能立刻看到「服务端已重启 + 版本 + 新增功能」，主会话能**自动、且只自动一次**地收到「继续执行」的指令，把断点工作续上。
- **真实事故（重复执行问题）**：早期实现曾出现两类「同一件事被反复执行」的缺陷，驱动了本机制的持续加固：
  1. **排队消息重复送达**：队列快照（work.json 的 `queues` 字段）与活队列之间的时序/归属不一致，导致已被消费的排队消息被「恢复逻辑」误判为「重启丢失」→ 以用户身份重新注入，同一条消息每 20s 被恢复一次（见 `2026-09-02`、`2026-09-04` 两份 bug 文档）。
  2. **续跑指令连发**：`followup` 注入会同步唤醒 idle agent → 触发 `agent/status running` → 重入 `tryResumeIfPending`，在指纹写盘前再次注入，同一批待办连发多条（见 `11cf8b0`）。

**边界（做什么 / 不做什么）：**

- 做什么：把「进行中事项（activity）+ 待办清单（pending）」持久化；重启后向**归属会话**的 agent 注入一次续跑指令；把「用户排队消息」跨重启快照/恢复；与手机端「中断 keep 模式」协同，让「仅终止保留」后的队列自动被新一轮循环消费。
- 不做什么：不做通用消息中间件；不保证 Agent「一定」完成续跑（续跑是注入一条指令，执行仍由 Agent 自主）；不做跨机器/多实例的分布式工作队列（当前单机 `$DSH_HOME/remote-control-work.json`）。

## 二、核心需求点拆解

1. **可持久化**：进行中事项与待办清单能跨进程重启存活（落盘为 work.json）。
2. **自动唤醒**：重启后无需客户端发问，服务端主动把续跑指令注入主会话 agent。
3. **恰好一次注入**：同一批待办（内容未变）只注入一次，跨触发源、跨重试、跨重入都不重复。
4. **会话归属正确**：续跑指令投递到 `sessionId` 归属的会话，不串到其它会话/子代理。
5. **队列跨重启恢复**：用户排队消息（含排队/插队）在进程重启或 agent 晚挂载后不丢，丢了才恢复。
6. **不重复投递框架消息**：子代理收尾/报告、LSP 反馈等框架注入消息绝不作为「用户排队消息」被恢复。
7. **与中断语义协同**：`interrupt(mode=keep)` 后，保留的排队消息自动重新投喂并唤醒新一轮 Agent 循环。

## 三、核心指标拆解

| 指标 | 达标口径 | 测量方法 |
| --- | --- | --- |
| 续跑送达延迟 | 服务重启 → 续跑指令送达主会话 agent：**毫秒级**（agent 已挂载）/ agent 挂载后**立即**（agent 晚挂载），不依赖 20s 兜底定时器 | 服务端日志「自动续跑：向 agent … 注入续跑指令」的时间戳与 boot 时间戳之差；smoke 断言「boot 立即注入」「agent/created 即时注入」 |
| 注入次数 | 同一批待办**恰好 1 次**，跨 boot/定时器/agent/created/agent/status 重入均不重复 | smoke 断言「重入触发源下同批待办只注入一次」「跨触发源同批待办不重复注入」 |
| 队列恢复准确率 | 真丢失的用户排队消息 100% 恢复；已消费/框架消息 0% 误恢复 | smoke 断言「防抖窗口内已消费消息不被重复恢复」「子代理收尾通知不入队列快照」 |
| 幂等健壮性 | 进程重启后仍能凭磁盘指纹识别「已注入」，不因内存锁丢失而重复 | `resumeFingerprint` 落盘 + 单元/冒烟覆盖 |

## 四、预期收益

- **用户体验**：重启后手机端立刻看到「服务端已重启」，主会话自动续跑，长任务断点续接、不丢上下文。
- **可靠性**：把「重复执行/丢消息/跨会话串扰」三类事故从机制层面根除（而非逐个打补丁）。
- **可维护性**：幂等判定集中在一处指纹 + 一处重入锁，后续任何新触发源接入自动继承幂等保证。

## 五、技术方案设计

### 5.1 持久化数据模型（work.json）

文件：`$DSH_HOME/remote-control-work.json`（权限 0600）。

| 字段 | 类型 | 写入方 | 语义 |
| --- | --- | --- | --- |
| `activity` | `string \| null` | Agent（重启前） | 当前进行中事项（一句话） |
| `pending` | `string[]` | Agent（重启前） | 待办清单（重启后按序继续） |
| `notes` | `string[]` | Agent/服务端 | 最近一次重启的新增功能说明（推给重连客户端） |
| `sessionId` | `string?` | Agent（重启前） | 待办所属会话（归属） |
| `resumeFingerprint` | `string?` | bridge（自动续跑后） | 已注入过的待办指纹（幂等标记） |
| `queues` | `Record<sessionId, QueueSnapshot>` | bridge（队列变化时） | 各会话「用户排队消息」快照（跨重启恢复用） |
| `updatedAt` | `number` | 任意写入方 | 最后写入时间 |

`QueueSnapshot = { items: {id, placement, text}[], at }`；`placement` 取值 `queued`（排队）/ `steering`（插队）/ `context`（框架注入，仅展示、不入快照）。

### 5.2 指纹幂等判定（恰好一次的核心）

```
resumeFingerprint = activity + "\n" + pending.join("\n") + "\n" + sessionId
```

- 注入前读盘计算 `fp`，若 `work.resumeFingerprint === fp` 说明这批待办已注入过，直接跳过；否则注入成功后把 `fp` 写回 `resumeFingerprint`。
- **两层防重**：
  1. **磁盘指纹（跨 tick）**：`resumeFingerprint` 持久化，进程重启、多个 macrotask（boot 定时器 + 20s interval + 事件）之间的重复由它兜住。
  2. **进程内重入锁（同 tick）**：`followup` 唤醒 idle agent 会**同步**触发 `agent/status running` → 重入 `tryResumeIfPending`；此时指纹尚未写盘，仅靠磁盘指纹挡不住。故设 `resumeInjecting` 布尔锁：`followup` 前置 `true`、`finally` 复位，重入调用直接 return。
- 关键实现约束：**指纹在 followup 成功后才写盘**（避免「写盘了但注入失败」导致永久漏注入），重入窗口交给内存锁兜住。

### 5.3 sessionId 归属（防跨会话串扰）

注入目标选择顺序：

1. `work.sessionId` 存在 → 优先 `agentOf(work.sessionId)`（精确归属）。
2. 归属会话未挂载 / 未指定 → 回退 `live.find(a => !isSubagent(a)) ?? live[0]`（第一个非子代理 live agent）。

目的：续跑指令投给「写待办的那个会话」的 agent，而不是随便投给任意 live agent 或子代理。

### 5.4 触发源（延迟根治的关键）

| 触发源 | 时机 | 覆盖场景 |
| --- | --- | --- |
| boot 立即 `resumeTick()` | bridge `apply()` 内同步一次 | agent 在 bridge 加载前就已挂载（`agent/created` 早于监听器注册而错过） |
| `agent/created` 事件 | agent 挂载完成（含重启恢复的持久化会话） | agent 晚挂载、且挂载后停在 idle（不发 `running`） |
| `agent/status running` 事件 | agent 进入 running | 阻塞解除/新一轮循环开跑时补注入 |
| `setTimeout(resumeDelayMs=20s)` + `setInterval(20s)` | 定时器 | 纯兜底（事件早于 bridge 注册错过 / agent 一直不挂载） |

`DSH_REMOTE_RESUME_DELAY_MS` 可调小首轮兜底间隔（测试用）；`DSH_REMOTE_RESUME=0` 整体关闭。

### 5.5 排队消息快照与恢复（restoreQueueIfLost）

- **快照写入**：`agent/inbox/spliced` 事件后，把「用户来源消息」投影（`userQueueItemsOf`，只收 `source.kind === 'user'`）经 **2000ms 防抖** 写入 `work.json.queues[sessionId]`。
- **恢复对比**：`restoreQueueIfLost(sessionId)` 在对比前先 `flushQueueSnapshot`（把防抖挂起的写入立即落盘，让磁盘状态追上真实活队列），再取「快照有、活队列没有」的差集 = 真丢失的消息，逐条 `followup` 重注入，最后清掉该会话快照。
- **三重防重复**：
  1. `flushQueueSnapshot` 消除「防抖窗口内陈旧快照 vs 活队列」的时序竞态（`cc35dc8`）。
  2. `userQueueItemsOf` 只把「用户消息」纳入快照/恢复，框架注入消息（子代理收尾/报告/LSP 反馈）永不入快照（`970b477`）。
  3. `restoringSessions` 集合 + `placement==='context'` 防御，阻断重入与陈旧快照的重复注入（`11cf8b0`）。

### 5.6 与「中断 keep 模式」的协同

`interrupt` 命令新增 `mode`（`clear`=终止并清空排队，旧行为；`keep`=仅终止当前循环、保留排队）：

```
keep: 快照 inbox 中 source.kind==='user' 的消息
      → a.cancel({kind:'user'})        // 终止当前循环
      → 对每条快照 a.followup(原文)     // 重投，既保留全文又同步唤醒 idle agent
```

这与自动续跑共用同一套「`followup` = 注入 inbox + 唤醒」机制：两者都通过 `followup` 把消息送入 `nextTurn` 并唤醒 driver，因此**天然继承**了指纹/快照的幂等与归属约束，不会与自动续跑互相重复投递（决策④「仅终止保留后自动启动新一轮 Agent 循环消费」）。

### 5.7 关键流程（文字图）

```
服务重启
  │
  ├─ bridge boot：loadWorkState(WORK_FILE) → 日志/hello/health 下发
  ├─ 立即 resumeTick()
  │     ├─ tryResumeIfPending：pending 非空 && 指纹未命中 → 选归属 agent → followup(续跑指令) → 写指纹
  │     └─ restoreQueueIfLost：flush 快照 → 差集 → followup(丢失消息) → 清快照
  │
  ├─ agent/created / agent/status running → 同上（幂等，已注入则跳过）
  └─ setTimeout(20s) + setInterval(20s) → 同上（纯兜底）

用户手机「中断」→ interrupt(mode=keep)
  │
  └─ 快照用户消息 → cancel → followup 重投 → 唤醒新一轮循环消费
```

## 六、多方案优劣势对比

三种「驱动续跑」的基础机制：

| 维度 | 方案A：纯定时重试 | 方案B：纯事件驱动 | 方案C：持久化队列 |
| --- | --- | --- | --- |
| 核心思路 | 固定间隔（如 20s）轮询 work.json，发现待办就注入 | 监听 `agent/created`/`agent/status` 事件，事件一到就注入 | 把工作/消息做成持久化队列，重启后重放 |
| 送达延迟 | 差：最长一个轮询周期（20s） | 好：agent 挂载/上线即注入 | 中：取决于队列重放触发时机 |
| 丢消息风险 | 高：进程在两次轮询间崩溃则待办丢失 | 中：事件早于监听器注册会错过 | 低：有落盘队列兜底 |
| 重复投递风险 | 中：需额外幂等 | 高：多事件源叠加易重入 | 高：重放与活队列叠加易重复 |
| 跨会话串扰风险 | 中：无归属约束会投错会话 | 中：同上 | 中：需按会话分桶 |
| 实现复杂度 | 低 | 中 | 高（需引入真正的队列语义/消费位点） |
| 维护风险 | 低 | 低 | 高（自研队列语义易踩一致性问题） |

**风险三维的对应治理（根治版选择「三者协同」）：**

- **重复投递**：定时轮询与事件驱动都会「多源触发」，根治版用「磁盘指纹 + 内存重入锁」保证同一批待办恰好一次；队列恢复用「flush 对齐时序 + userQueueItemsOf 归属筛选 + restoringSessions 重入锁」保证消息恰好一次。
- **丢消息**：纯事件驱动靠不住（事件错过即丢），根治版保留「持久化快照（work.json.queues）+ 持续重试兜底」，真丢失才恢复、不丢。
- **跨会话串扰**：用 `sessionId` 归属 + `agentOf` 优先，把续跑指令精确投到写待办的会话；队列快照按 `sessionId` 分桶。

结论：**不选单一机制**。根治版 = **事件驱动为主（低延迟）+ 定时重试兜底（防事件错过/agent 不挂载）+ 持久化快照恢复（防丢消息）**，并以「指纹幂等 + 归属 + 重入锁」统一治理三类风险。

## 七、最终选择与决策逻辑（根治版）

**演进主线**（对应元信息 commit）：

1. `3862e1b` / `9d8e326`：初版「一次性定时器」——boot 后延时向主 agent 注入一次。**缺陷**：agent 晚挂载时直接放弃（「暂无 live agent」就再也不试），是「重启后经常恢复不了任务」的根因。
2. `a1d722e`：**根治版核心**——从「一次性」改为「持续重试 + 指纹幂等 + sessionId 归属」。内容未变不重复注入；每 20s 重试；优先唤醒 work.sessionId 所属会话。
3. `11cf8b0`：补上两个被用户实测发现的漏洞——① boot 只排定时器、无立即尝试，且只监听 `agent/status running`（idle 挂载不触发），导致「重启后要等好久才续上」；② `followup` 同步唤醒重入、指纹写盘晚于 followup，导致「阻塞后连发多条续跑指令」。修复：boot 立即尝试 + `agent/created` 事件 + 内存重入锁。
4. `cc35dc8`（队列）：「快照防抖 2000ms 的滞后镜像」被恢复逻辑当成权威事实对比 → 恢复前先 `flushQueueSnapshot` 对齐时序（教训：**异步投影不能当权威事实**）。
5. `970b477`（队列）：「供展示的全量投影」被复用作「供恢复的权威状态」→ 拆出 `userQueueItemsOf`，只把用户消息纳入快照/恢复（教训：**一个快照必须明确它归属哪类状态**）。

**为什么这样决策（对照第六节）：**

- **弃纯定时**：送达延迟不可接受（用户明确「不是简单调小间隔」）。
- **弃纯事件**：事件错过/agent 不挂载时无兜底，会丢续跑。
- **弃自研持久化队列**：引入真正的队列语义（消费位点/ack）复杂度与一致性问题远超收益，当前单机场景用「快照 + 差集恢复」已足够。

**最终拍板**：用户认可「持续重试 + 指纹幂等 + work.json sessionId 归属」为根治版方向（AGENTS.md 历史决策记录）。落地为：**事件驱动（agent/created + agent/status）为主触发，boot 立即尝试 + 定时器兜底，work.json.queues 快照恢复，指纹 + 内存锁 + 归属 + 归属筛选四道幂等**。

## 八、对现有架构的影响

- **改动面**：集中在 bridge 的 `src/core.ts`（续跑/队列/中断逻辑）与 `src/work.ts`（work.json 读写）。协议侧仅 `interrupt` 命令增加 `mode` 字段、`queue_action`/`session_queue` 复用既有 `QueueItemWire`，无破坏性变更。
- **风险点**：
  1. `work.json` 目前是**非原子覆写**（直接 `writeFileSync`），flush 与常规防抖写并发时理论上有半写风险（已在 bug 文档列为后续项）。
  2. `resumeFingerprint` 是「内容哈希」而非「消息幂等键」——Agent 若在续跑过程中**主动改写 work.json**（更新 activity/pending），指纹变化会触发再次注入（属预期「新内容=新续跑」，但需在文档层面明确该语义）。
- **兼容性/回滚**：`DSH_REMOTE_RESUME=0` 可整体关闭；`mode` 缺省回落 `clear`（旧行为）；work.json 字段均为可选，旧文件无 `resumeFingerprint`/`queues` 时自然退化。回滚即恢复旧二进制，无持久化格式破坏。

## 九、后续迭代规划

**与九项决策④（中断语义）的联动：**

- 决策④：有排队消息时弹框二选一（终止并清空 / 仅终止保留，加取消）；「仅终止保留」后队列仍有待执行消息时**自动启动新一轮 Agent 循环消费**。
- 落地：`interrupt(mode=keep)`（`7b23081`）＝「快照用户队列 → `cancel` → `followup` 重投」。`followup` 重投与自动续跑的 `followup` 注入是**同一套 wake+inbox 机制**，因此中断 keep 的重投也自动处于指纹/归属约束之下：重投的是「保留的排队消息」，与「续跑指令（pending 待办）」是两个不同通道，互不重复；且 keep 重投会唤醒 idle agent，直接满足决策④的「自动消费」。
- **边界与后续**：
  1. **消息幂等键（`clientMsgId`）仍待议**：当前续跑靠「内容指纹」、队列靠「id/文本差集」，属于「内容级去重」；若未来引入更多多源恢复路径，建议给每条用户消息加客户端幂等键，让重复注入在**消费端**可去重（纵深防御，`cc35dc8`/`970b477` 均已列为后续）。
  2. **work.json 原子写**：改「临时文件 + rename」消除并发写半读风险。
  3. **审计其它「派生投影当权威状态」**：检查 `resumeFingerprint`、会话列表合并持久化层等，是否还有把滞后投影当单一事实源的地方。
  4. **触发再评估条件**：出现多实例/跨机器部署、或续跑需求扩展到「真正的工作队列（多步依赖、重试策略、死信）」时，再评估引入正经队列中间件，替换当前的「快照 + 差集恢复」。
