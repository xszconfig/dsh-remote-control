## 一、需求背景

- **为什么做这件事**：DSH Remote Control 需要一个「受控调试」能力——让 Agent 在桌面端 `node --inspect-brk=0 <脚本>` 起一个调试进程，手机端看断点命中现场的调用栈/作用域/变量，并下发 `继续/单步/跳出/停止/读变量` 指令。核心诉求是「Agent 排查自己写的脚本时，能在手机上逐步看到执行现场」。
- **边界（做什么/不做什么）**：
  - 做：断点设置、暂停现场（栈帧+作用域+变量惰性展开）、单步/继续/停止、stdout/console 输出流、未捕获异常提示；
  - 不做：表达式求值（evaluate/watch）、条件断点/日志断点、性能剖析（Profiler）、内存快照、浏览器页面调试——这些当前不在需求内，但 CDP 本身都具备，未来可增量加。

## 二、核心需求点拆解

1. **启动受控调试进程**：按 `sessionId` 归属隔离，一个会话一个调试进程，重复启动报错。
2. **断点**：支持按文件+行号（1-based）设断点，断点未命中可执行行时给出可读提示。
3. **暂停现场**：断点命中后下发「原因 + 停止位置 + 调用栈帧 + 每帧作用域」。
4. **变量读取**：按作用域引用（variablesReference）惰性拉取变量，区分「有子节点/无子节点」。
5. **单步控制**：继续(resume)/单步(stepOver)/跳出(stepOut)/停止(stop)。
6. **输出流**：stdout 与 console.log 双通道去重，最多保留最近 N 行。
7. **会话生命周期**：进程自然退出/失败后自动从注册表移除，允许同会话再次启动。
8. **传输无关**：调试状态经 WS 广播到手机（`debug_state`/`debug_output`/`debug_variables`），Agent 侧经工具 `debug_start`/`debug_command` 下发。

## 三、核心指标拆解

| 指标 | 达标口径 | 测量方法 |
| --- | --- | --- |
| 断点命中正确性 | 命中即上报暂停现场，`stoppedAt` 行号与断点一致（1-based） | smoke `断点命中：调用栈帧 + 行号 + 作用域` |
| 变量可读性 | 作用域对象能读到顶层变量名/值，有子节点返回 `hasChildren` | smoke `暂停现场变量（模块作用域可见 counter）` |
| 单步语义 | stepOver 从「循环体末句」落到「循环头」（CDP stepOver 语义） | smoke `单步：循环体末句 → 循环头` |
| 输出去重 | stdout 与 console 双通道不重复（`loop 3/done 3` 各一次） | smoke `console 输出流（无双行）` |
| 资源回收 | 卸载/停止时 kill 子进程 + 清定时器 + 清 pending | `debug.ts` `dispose()` 幂等释放 |
| 依赖成本 | 调试后端**零新增运行时依赖**（复用 `ws` + `node:child_process`） | `package.json` dependencies 仅 `qrcode`/`ws` |

## 四、预期收益

- **用户（手机端）**：像 IDE 一样在手机上逐步看 Agent 执行现场，Agent 排查「跑崩/跑挂」的脚本时能定位到具体行与变量。
- **Agent（桌面端）**：通过 `debug_start`/`debug_command` 工具闭环调自己写的东西，配合 LSP 诊断形成「编辑→诊断→调试」完整代码智能链路。
- **开发效率**：零适配器运维，`node --inspect` 直连，调试能力随 Node/Chrome 演进自然获得。

## 五、技术方案设计

### 5.1 总体架构（现状：CDP 直连，2 层）

```
手机 App ──WS(debug_state/output/variables)──▶ bridge src/core.ts
                                                 │ broadcast
                                        DebugManager（seam，传输无关）
                                                 │ hooks: onState/onOutput/onVariables
                                        InspectorSession（CDP 后端，Node 专用）
                                                 │ WebSocket(CDP) + spawn
                                        node --inspect-brk=0 <脚本>（Node Inspector）
```

- **`DebugManager`（seam）**：持有 `Map<sessionId, InspectorSession>`，对外暴露 `start/command/variables/variablesFor/stop/dispose/snapshotOf`，回调接口 `onState/onOutput/onVariables` 与传输无关（`src/debug.ts` 顶部注释明确「将来接 DAP 适配器可平替」）。
- **`InspectorSession`（CDP 后端）**：`spawn('node', ['--inspect-brk=0', program])` → 从 stderr 解析 `Debugger listening on ws://…` 拿 WS 地址 → `Runtime.enable` → `Debugger.enable` → `Debugger.setBreakpointByUrl` 设断点 → `Runtime.runIfWaitingForDebugger` 释放入口暂停；事件侧监听 `Debugger.paused/resumed`、`Runtime.consoleAPICalled/exceptionThrown`、`Debugger.scriptParsed`；变量侧 `Runtime.getProperties` 惰性展开。
- **wire 数据模型**（`src/protocol.ts`）：`DebugStateSnapshot` / `DebugPausedInfo` / `DebugFrameWire` / `DebugScopeWire` / `DebugVariableWire` / `DebugBreakpointWire`，手机端与 Agent 工具共用，服务端投影为准。

### 5.2 关键流程（断点调试）

1. Agent/手机发 `debug_start`（sessionId + program + cwd + breakpoints）→ `DebugManager.start()` 建 `InspectorSession` 并 `start()`。
2. `InspectorSession` spawn `node --inspect-brk=0`，脚本停在入口（`-brk` 等待调试器）。
3. 连上 Inspector 后先注册断点（`setBreakpointByUrl`，`realpath` 对齐 macOS `/tmp→/private/tmp`），再 `runIfWaitingForDebugger` 释放；首个 paused 是入口暂停，自动 resume 一次（`entryArmed` 防竞态）。
4. 用户断点命中 → `Debugger.paused` → 上报 `DebugStateSnapshot{state:'paused', frames, stoppedAt}` 经 WS 广播到手机。
5. 手机下发 `resume/step/step_out` → `InspectorSession.command()` → `Debugger.resume/stepOver/stepOut`；`variables` → `Runtime.getProperties` 惰性展开。

## 六、多方案优劣势对比

> 三条候选路线（对照 `docs/debug-protocol-cdp-vs-dap.md` 第 7 节）：
> **方案 A = CDP-only（现状）**、**方案 B = DAP 客户端 + 各语言适配器（OMP 路线）**、**方案 C = 每语言原生协议各写一个后端（pydevd/delve/jdwp 各接各的）**。

| 维度 | A. CDP-only（现状） | B. DAP 客户端 + 适配器 | C. 每语言原生协议 |
| --- | --- | --- | --- |
| 协议成熟度 | 高：Chromium/Node **内建**，随 Chrome 演进，DevTools 验证充分 | 高：微软 2016 中立标准，LSP 姊妹协议，VS Code 背书 | 参差：各语言调试器协议成熟度不一，jdwp/pydevd 各成体系 |
| 语言覆盖面 | **仅 Node/Chrome 系**（本产品调试对象正好是 Node 脚本） | 语言无关：js-debug / debugpy / gdb -i dap / lldb-dap / delve 官方或社区适配器齐全 | 可覆盖，但客户端代码 N 份 |
| 断点·变量·单步能力 | 齐全（断点/栈/作用域/变量/stepOver/stepOut/resume）+ 额外 console/Network/Profile | 齐全（断点/条件断点/栈/变量/表达式），IDE 调试视图语义 | 齐全但各写各的映射 |
| 实现成本 | **最低**：零新增依赖，复用 `ws`+`child_process`，2 层直连 | 中：需安装/管理适配器二进制，多一层进程，launch/attach 配置 | 高：每语言写一套协议客户端 |
| 生态工具 | Puppeteer/Playwright 成熟 | VS Code / nvim-dap / OMP 通用 | 各调试器自带 |
| 未来扩展（Python/Go/Rust） | **不支持**（需换 DAP 或原生协议） | 天然支持：加一个适配器即可 | 支持，但成本线性增长 |
| 维护风险 | 低（零运维） | 中（适配器版本/路径管理） | 高（N 份客户端维护） |
| License | 无新增（内建协议） | 适配器各带 license（debugpy MIT、js-debug MIT…） | 各调试器 license 不一 |

**事实依据（不凭印象）**：
- CDP 是 Chromium/Node 内建协议，Node 22 可直接 `--inspect`；DAP 是微软 2016 发布的中立标准，生态含 js-debug/debugpy/gdb -i dap/lldb-dap/delve（见 `docs/debug-protocol-cdp-vs-dap.md` §2）。
- 行业现状：主流 coding agent 的 IDE 壳多为 Electron/Chromium 栈，调试目标多为 Node/TS 脚本，且浏览器上下文调试**只能走 CDP**（OMP 反而要再包一层 DAP 适配器）——三点都强化 CDP 路线（同文档 §5）。
- 本项目产品定位：控制本机**一个 Node 内核的 harness**，调试对象是 agent 在 Mac 上跑的脚本——Node/TS 全覆盖（同文档 §6）。

## 七、最终选择与决策逻辑

**选：方案 A（CDP-only，维持现状）。**

决策逻辑（对照第六节逐条）：

1. **产品边界决定语言面**：调试对象是「本机 Node 内核 harness 上 agent 跑的脚本」，Node/TS 全覆盖；「多语言调试」目前是**伪需求**（Python 诊断已支持，调试未在规划内）。
2. **零依赖是最硬的约束**：当时本机无 VS Code/js-debug 适配器，也不愿为「可能用不上」的能力引入大型依赖与适配器运维；CDP 直连复用 `ws`+`child_process`，2 层、延迟最低。
3. **能力面更贴合**：CDP 的 console/Network/Profile 超出 DAP 的纯「断点/变量/表达式」语义，更契合「agent 排查自己代码」的场景。
4. **seam 已预留，决策可逆**：`DebugManager` 回调接口与传输无关，未来接 DAP 只需新增后端类平替 `InspectorSession`，手机面板/Agent 工具/WS 协议全部复用——**当前选 CDP 不锁死未来**。
5. **为什么不选 B/C**：B 的多适配器运维与三层结构对「当前只有 Node」是纯负担；C 的「每语言各写客户端」在没多语言需求时最不经济。

**拍板约束（依据 AGENTS.md 历史决策 + 铁律 1）**：调试协议属重大技术选型。历史决策明确记录——「当前用 CDP（Node Inspector）直连，零依赖但仅 Node；`DebugManager` 回调接口已预留 DAP 平替 seam。**未来若扩语言（Python/Go/Rust）必须先问用户**再实施 DAP 后端。」即：**现状维持 CDP；一旦出现 Python/Go/Rust 等非 Node 调试需求，不得擅自上 DAP，必须先停下来问用户拍板**，届时以本文第六节对比为论证底稿再走铁律 1 流程。

## 八、对现有架构的影响

- **改动面（现状 CDP 已落地）**：仅新增 `src/debug.ts`（CDP 后端 + `DebugManager` seam）+ `src/protocol.ts` 调试 wire 类型 + `src/core.ts` 里两处胶水（REST `debug/start`、`debug/stop` 路由 + Agent 工具 `debug_start`/`debug_command` 注册 + `debug_state/output/variables` 广播）。
- **依赖**：零新增运行时依赖（`package.json` dependencies 仍只有 `qrcode`/`ws`）。
- **风险点**：
  - `--inspect-brk=0` 用随机端口，靠 stderr 行拿地址，配 10s 兜底超时（`connectTimer`）；脚本自身打印含 `Debugger listening` 的行会被误判——已用 `entryArmed`/`breakpointsDone` 处理入口竞态，但仍是脆弱点；
  - macOS `/tmp→/private/tmp` 软链导致断点 URL 与脚本实际 URL 不一致 → 断点静默失效，已用 `realpathSync` 对齐（`debug.ts`）。
- **兼容性/回滚**：seam 设计使「回滚 CDP 行为」= 直接改 `InspectorSession` 内部，不动 `DebugManager` 与 wire 协议；协议侧 `DebugStateWire` 等字段用可空/默认值，手机端旧版本可安全忽略新增字段。

## 九、后续迭代规划（含 DAP 平替接入点与影响）

### 9.1 DAP 平替接入点（seam 到底在哪）

`src/debug.ts` 已把「传输无关的会话契约」与「CDP 具体实现」拆开，平替点只有一处：

- **稳定接口（不动）**：`DebugManager` 的 `start/command/variables/variablesFor/stop/dispose/snapshotOf` + hooks `onState/onOutput/onVariables` + wire 类型 `DebugStateSnapshot`/`DebugPausedInfo`/`DebugFrameWire`/`DebugScopeWire`/`DebugVariableWire`/`DebugBreakpointWire`。
- **可替换实现（唯一改动点）**：`InspectorSession`（CDP 专用，~340 行）——实现一个同契约的 `DapSession`（或按语言 `DebugpySession`/`DelveSession`/`LldbDapSession`），内部把 DAP 的 `launch/attach` + `stopped/continued` 事件 + `stackTrace/scopes/variables` 请求 + `continue/next/stepOut` 映射成**同一套 wire 快照**，经同一 hooks 上报。
- **选择后端的方式**：`DebugManager.start()` 按 `program` 扩展名/语言（或显式 `language` 参数）路由到 CDP 或对应 DAP 后端；Node 继续走 `InspectorSession`，其余走 DAP 适配器。
- **协议侧影响**：手机端/Agent 工具的 wire 协议**零改动**（复用现有 `debug_state/output/variables` 事件与 `debug_start/debug_command` 工具），因此 App 侧无需升级。

### 9.2 上 DAP 的影响面（届时须评估）

- 新增依赖：适配器二进制（debugpy/delve/lldb-dap 等）的安装/路径管理 + DAP 客户端（stdio Content-Length 帧，类似 LSP 的 `lsp.ts` 可复用同款帧解析）；
- `DebugManager` 需从「单后端」改为「按语言多后端注册表」，`start()` 的 `cwd`/`breakpoints` 映射为 DAP `launch` 配置；
- 现有 CDP 特定逻辑（stderr 解析 WS 地址、`entryArmed` 入口暂停、console 双通道去重）不适用于 DAP 后端，需在 `DapSession` 内单独实现等价语义；
- 冒烟测试需补「每语言后端」的 mock 契约（当前 mock 只覆盖 CDP 通道）。

### 9.3 触发再评估的条件

- 出现 Python/Go/Rust/JVM 任一的**调试**需求（诊断已有，不算）→ 触发铁律 1 流程，拿本文第六节做论证底稿请示用户；
- 在此之前，维持 CDP-only，不做任何 DAP 预埋实现（只保留 seam，不提前写 DapSession，避免死代码）。
