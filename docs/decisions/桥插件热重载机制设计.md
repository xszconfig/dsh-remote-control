> 本文档是「bridge 插件热插拔/可逆性/热重载机制」的正式技术设计文档，面向主仓库的决策台账归档。实现细节与最新机制以 bridge 仓库 `docs/hot-reload.md` 及 `src/reloader.ts` 为准。

## 一、需求背景

- **痛点**：`dsh-remote-control-bridge` 是 DSH 的 Web 插件（Cordis 框架，入口 `lib/index.js`）。早期任何业务改动——LSP 诊断、调试器、审批透传、自动续跑——都要**重启整个 DSH 服务端**才生效：中断所有进行中会话、打断长连接与 LSP 子进程、重新走一遍 boot 自检与自动续跑，迭代成本高、且重启需用户确认（铁律 4）。
- **契机**：审计确认 bridge 存在「卸载不干净」的结构性缺陷——15 个 `register/registerUpgrade` 的返回值被丢弃，而 `@deepseek-ai/dsh-host-webserver` 对重复路径注册**直接 throw**（`webserver: duplicate route`）；一旦插件被 Cordis 卸载、路由残留指向旧闭包，二次 apply 必崩。这意味着 bridge 连「可被卸载」都做不到，更谈不上热插拔。
- **边界**：
  - 做：让 bridge 业务代码（`core.ts` 及其相对依赖图）能**免重启热替换**，且替换具备事务性（失败可回滚）。
  - 不做：不替换 shell/auth/reloader 三个稳定平面（改动仍需重启）；不热换 `node_modules` 依赖（升级依赖仍需重启）；不做 shell/core 之外的架构重构；不依赖官方 HMR（官方 HMR 在本部署已被禁用，链路不可控）。

## 二、核心需求点拆解

1. **可逆卸载**：插件被 Cordis 卸载后，全部路由/定时器/子进程/网络连接必须干净释放，二次 apply 不抛 `duplicate route`。
2. **免重启换业务代码**：改 `core.ts` 及其相对依赖后，通过一个受控入口（HTTP 端点）即可让新代码生效，不重启进程、不断开已连接手机。
3. **事务性与回滚**：换模块的每个阶段（复制→import→卸载旧→挂载新）失败都要有确定性结局——旧版本继续运行，并留下可观测的错误（`lastError`）。
4. **自动触发（可选）**：`fs.watch` 监听部署 `lib/` 目录，文件变化自动触发换模块；但可被环境变量关掉（逃生开关）。
5. **版本可观测**：暴露 `/remote/hot` 状态端点，返回 shell 版本、core 版本、reload 次数、最近一次错误，便于部署后自证。

## 三、核心指标拆解

| 指标 | 达标口径 | 测量方法 |
| --- | --- | --- |
| 热换生效时长 | 从触发到新 core 路由可用 < 2s（复制 + import + 重挂载） | `POST /remote/reload` 后立即 `GET /remote/hot` 看 `coreVersion` 变化 |
| 免重启 | 热换期间已连接 WS 客户端不断开、进程 PID 不变 | reload 前后对比 `health` 的 `version` 与进程存活 |
| 回滚可靠性 | import 失败/apply 抛错时旧版本仍可服务 | 注入坏 core.js 触发 reload，验证 `lastError` 且旧路由仍响应 |
| 卸载干净度 | dispose 后二次 apply 不抛 `duplicate route`、无残留定时器/子进程 | Phase A 后冒烟 + 人工二次 apply 验证 |
| 内存增长（已知开销） | 每次 reload 旧 ESM 模块图不可回收，开发期可接受 | 长期高频 reload 监控 RSS 增长，必要时重启回收 |

## 四、预期收益

- **迭代效率**：业务代码改动「`pnpm build` → `cp -R lib/*` → `POST /remote/reload`（或 watcher 自动）」即可生效，免去 DSH 重启的会话中断与 boot 开销；热插拔上线后，lsp_query/debug 工具超时修复等都以「热重载上线」方式交付。
- **稳定性**：Phase A 可逆性补齐后，插件可被 Cordis 干净卸载，杜绝「卸载残留 → 二次 apply 崩溃」这一类隐性地雷；也为后续 Cordis 层面的插件生命周期治理打底。
- **可观测**：`/remote/hot` 提供 reload 计数、版本、错误，部署后能自证「这次到底换没换成」。

## 五、技术方案设计

### 5.1 总体架构：薄壳 + 版本化暂存目录

```
进程内
  shell  lib/index.js（稳定薄壳，此后几乎不再改）
   ├─ 导出 { name, inject, apply }；apply 为 async 函数
   ├─ ReloadController  lib/reloader.js（稳定平面，DI 可单测）
   │     · initialLoad / reload / startWatcher / stopWatcher / dispose
   │     · 状态字段 reloads / lastReloadAt / lastError / watching / currentVersion
   │     · reload()：copy 暂存 → import 新 core → dispose 旧 fiber → ctx.plugin 新 core
   ├─ 两个自举路由（鉴权与 core 同款 allowLocalOrEnvToken）
   │     · POST /remote/reload   触发热换
   │     · GET  /remote/hot      { ok, shell, reloads, lastReloadAt, lastError, watching, coreVersion }
   ├─ fs.watch(lib/)  debounce ~400ms → reload()
   └─ ctx.effect 清理：逆序释放两路由 disposer → watcher.close → dispose core fiber

  core  lib/core.ts（业务整体，随版本目录热换）
   ├─ name = 'dsh-remote-control-bridge-core'；inject/apply 与原 index.ts 完全一致
   ├─ 相对依赖 ./protocol.js、./lsp.js、./lsp-feedback.js、./debug.js、./work.js、./logger.js、./auth.js
   └─ bare 依赖 ws / qrcode / @deepseek-ai/*（经 staging/node_modules 合并式符号链接解析）

磁盘
  ~/.dsh/bridge-reload/
   ├─ <ts-1>/   上一代（保留，回滚用）
   └─ <ts-2>/   当前代
   （其余删除；每次 reload 的旧 ESM 模块图留在进程模块表，不可回收）
```

### 5.2 关键机制：为什么「换目录」就能整体热换

ESM 模块缓存**按文件 URL 键控**。每次 reload 把部署目录 `lib/` 里的全部 `*.js` 复制进一个**全新的、时间戳命名的暂存目录**，再 `await import(<该目录>/core.js)`。新目录 = 全新缓存键，`core.js` 及其全部**相对静态依赖**（`./protocol.js`、`./lsp.js`、`./work.js` …）整体换新——core 内部的 `import './x.js'` 一行不用改。这是「版本化暂存目录」成为核心手段的原因：**绕开 ESM 缓存，不做任何模块热替换 hack**。

### 5.3 bare import 解析：collectNodeModules 合并祖先 node_modules

`ws` / `qrcode` / `@deepseek-ai/*` 按「从导入文件所在目录**逐层向上**找 `node_modules`」解析，而暂存目录位于部署包目录树之外，向上找不到。因此复制时在暂存目录内建一个**真实目录** `node_modules`，把**所有**祖先 `node_modules` 的顶层条目合并式符号链接进来：

- 从 `srcDir` 向上收集每一个祖先 `node_modules`（直到文件系统根）；
- 按最近→最远遍历，同名条目先到先得、后到的跳过（近层优先，与 Node 逐层向上「最近命中」语义一致）；
- 单个 symlink 失败（EEXIST/EPERM/平台不支持）只跳过该条目，不中断复制。

> **为什么必须合并而不是单目标链接**：pnpm 把依赖分层存放——近层（`~/.dsh/profiles/web/node_modules`）只有 `qrcode`/`ws`，远层（`~/.dsh/profiles/node_modules`）才有 `@deepseek-ai/*`。只链最近一层会导致 `import '@deepseek-ai/cordis'` 解析失败（`ERR_MODULE_NOT_FOUND`）。这是 `6d5da59` 修复的根因，详见 bridge `docs/bugs/2026-09-02-hot-reload-first-activation-import-fail.md`。

### 5.4 事务式 reload 与回滚语义

`ReloadController.doReload()` 的顺序：

1. `stage()`：复制 `lib/*.js` 到新版本化目录（目录名含时间戳，冲突加序号）。
2. `importCore()`：`await import(<新目录>/core.js)`。**import 失败 → 不动旧实例**，只记 `lastError`，旧版本继续运行。
3. `dispose 旧 fiber`：先卸载旧 core（Phase A 的 effect 清理路径生效——路由 disposer 逆序释放、LSP/Debug/定时器裸资源清理）。
4. `ctx.plugin(mod)` 挂新 core。**新 apply 抛错 → 用保留的上一代模块引用重新 `ctx.plugin` 旧模块**，旧 fiber 重新可用，记 `lastError`。
5. `prune()`：只留「当前 + 上一代」目录，其余删除。

- **重入锁**：`reload()` 进行中再次触发返回 `busy`（HTTP 409）。
- **启动幂等**：`initialLoad()` 已有活跃 fiber 时直接返回 `ok`；core 缺失/import 失败只记 `lastError`、不崩进程，等下次 watcher/端点重试。

### 5.5 两个触发入口 + 逃生开关

- `POST /remote/reload`：手动触发热换（loopback 或带 `DSH_REMOTE_TOKEN`）。
- `fs.watch(libDir)`：debounce ~400ms 后自动触发；`DSH_REMOTE_HOT_RELOAD=0` 只关 watcher，端点仍可用。
- 两个路由鉴权与 core 同款 `allowLocalOrEnvToken`（loopback + Host 头校验，或 Bearer token）。

## 六、多方案优劣势对比（完整重启 vs 热重载 vs 文件监听实时换模块）

| 维度 | 方案A：完整重启 | 方案B：手动热重载（POST /remote/reload） | 方案C：文件监听实时换模块（fs.watch） |
| --- | --- | --- | --- |
| 生效速度/迭代反馈 | 最慢：重启 DSH + boot 自检 + LSP 冷启动，数十秒 | 快：秒级（copy+import+重挂载 <2s） | 最快：改→build→cp 后自动生效，零人工 |
| 中断影响 | 大：断开所有会话/长连接/LSP 子进程，需自动续跑兜底 | 极小：仅 dispose 旧 core → 重挂新 core，已连 WS 不断 | 小：同 B，但无人工确认窗口 |
| 原子性/回滚 | 进程级隔离，天然干净 | 事务式（copy→import→dispose→apply）+ 回滚到上一代 | 同 B，但**部署 `cp -R` 逐文件复制中途触发会 import 到「半套新旧混装」的不一致版本** |
| 状态干净度 | 最高：无残留模块图/文件句柄 | 中：旧 ESM 模块图随每次 reload 累积（不可回收） | 中：同 B，且 watch 风暴会加剧 |
| 运维复杂度 | 低（但要用户确认，铁律 4） | 中：需显式 curl 或脚本触发 | 低：部署即生效，但需 debounce + 逃生开关 |
| 失败风险 | 低但代价高（一次中断） | 低：import/apply 失败都有确定性回滚 | **高**：半写文件、硬链接混装、无确认窗口、需防抖 |
| 适用场景 | 改 shell/auth/reloader、升级依赖、内存回收 | 主路径：业务代码迭代 | 便捷辅助：本地开发自刷，生产建议关闭 |

**结论**：以**方案B（手动热重载）为主路径**，方案C（fs.watch）作为**可选便捷辅助**（debounce + `DSH_REMOTE_HOT_RELOAD=0` 逃生开关）；方案A 保留用于「稳定平面变更 / 依赖升级 / 内存回收 / 首次激活」等必须重启的场景。三者不是互斥，而是按「改动层级」分工——改动越接近业务核心（core），越适合免重启热换；越接近框架承重墙（shell/auth/reloader/依赖），越必须重启。

## 七、最终选择与决策逻辑

### 7.1 选型：自举 shell + 版本化目录，不依赖官方 HMR

- **官方 HMR 被禁用**：DSH 本部署禁用了官方 HMR 链路，且官方 HMR 的换模块粒度/时序/回滚语义对插件不可控——无法精确保证「先 dispose 旧 fiber 再 apply 新 fiber」的事务性，也无法注入我们的回滚与 `lastError` 观测。
- **自举的核心价值**：用「版本化暂存目录 + 动态 import」绕开 ESM 缓存，**零 hack、语义可精确控制**（事务顺序、回滚、重入锁、状态端点全部自持），并天然复刻 Node 的逐层模块解析（`collectNodeModules`）。这是「可逆性 → 可热换」的最小、可控、可单测的实现路径。

### 7.2 两阶段落地（先可逆，后热换）

**Phase A（`1e4e896`）——可逆性：为热插拔打地基**

- 改动：15 个 `register/registerUpgrade` 返回值收集进 `routeDisposers`，卸载时逆序移除；`InspectorSession/DebugManager` 新增幂等 `dispose()`（kill Inspector 子进程、清 connect 超时与 stdout 去重定时器、清 pending）；`ctx.effect` 清理补齐 `broadcastStatTimer` / `resumeBootTimer` / thinkStreams 节流 timer / `lsp.dispose()` / `debug.dispose()`。
- 选型逻辑：**不做任何协议/行为/版本改动**，只补卸载路径。先保证「能干净卸载」——这是热插拔的**前置条件**：换模块的本质就是「dispose 旧 fiber → apply 新 fiber」，旧 fiber 卸不干净，热换必然残留崩溃。
- 验证：`pnpm build` 通过；`smoke` 118/118 两遍全绿。

**Phase B（`831385c`）——shell-core 拆分 + ReloadController**

- 改动：`src/index.ts` 拆为稳定薄壳（boot 经 ReloadController 挂载 core + 两个自举路由 + fs.watch + effect 清理）；`src/core.ts` = 原业务整体平移（`name` 改 `-core`、`BRIDGE_VERSION` 再导出、auth 六函数抽取，业务逻辑零改动）；新增 `src/reloader.ts`（事务式 reload/回滚/剪枝）、`src/auth.ts`（共用鉴权辅助）。
- 选型逻辑：Phase A 的 effect 清理路径，正是 Phase B 换模块时「dispose 旧 fiber」的执行者；先 A 后 B 保证**每一步独立可验证**——A 改完 118/118，B 在 A 之上 119/119 + `hotreload.test.mjs` 5 用例。
- 验证：`smoke` 119/119；`hotreload.test.mjs` 5 用例（含两层 node_modules 合并、回滚、剪枝）；`BRIDGE_VERSION` 0.13.0。

### 7.3 为什么不选其它

- 不选「仅完整重启」：无法满足免重启迭代的核心诉求（需求点 2）。
- 不选「仅文件监听」：部署 `cp -R` 逐文件复制 + 硬链接混装导致半写触发，无事务保障，风险不可控（见第六节方案C风险）。
- 不选「官方 HMR」：被禁用 + 换模块语义不可控，无法注入回滚与观测。

## 八、对现有架构的影响

- **改动面**：
  - `src/index.ts`（薄壳，~90 行）、`src/reloader.ts`（新增 332 行）、`src/auth.ts`（新增 48 行）、`src/core.ts`（业务整体平移，逻辑零改动）。
  - 协议/wire 格式**零改动**；`BRIDGE_VERSION` 0.12.0 → 0.13.0（协议号按常规 bump）。
  - `package.json` 依赖不变（仅 version bump）；无新增运行时依赖。
- **风险点**：
  - 旧 ESM 模块图随 reload 累积（内存缓慢增长，长期高频需重启回收）。
  - 稳定平面（shell/auth/reloader）改动需重启；首次激活需重启一次（见第九节）。
  - 热换只替换业务代码，依赖包不随热换更新。
- **兼容性与回滚方案**：
  - 运行期回滚：import/apply 失败自动回滚到上一代模块。
  - 部署期回滚：保留「上一代 + 当前代」暂存目录；彻底回退可 `cp -R` 旧 lib + 重启（最坏情况）。

## 九、后续迭代规划

### 9.1 已知坑（逐条记录，迭代时重点规避）

1. **部署包 `lib/` 硬链接混装**：实测部署目录 `~/.dsh/profiles/web/node_modules/dsh-remote-control-bridge/lib/` 里，`protocol.js`、`index.d.ts` 的 inode link count = 2（硬链接，与其它位置共享 inode），其余文件 link count = 1（独立副本）。混装状态下 `cp -R lib/*` 覆盖的写入语义不一致：硬链接目标被**原地截断写入**（污染共享 inode，后续 `pnpm install` 或其它引用点可能把内容改回去），独立文件才被替换；这也会让 fs.watch 触发次数与「真正生效的是哪个版本」变得不可预期。**迭代规划**：部署脚本统一为「新目录 + 目录级 symlink swap」或 `cp --remove-destination`/`rsync`（先删后写，强制换 inode），杜绝写入穿透硬链接。
2. **首次激活需重启一次**：旧进程里只有 Phase A 代码（`apply` 即业务本体，无薄壳/ReloadController/自举路由），不存在热换入口。部署 0.13.0 后**必须重启 DSH 一次**让薄壳加载；此后业务升级才可免重启。这是「自举」方案的固有代价（没有鸡就没有蛋）。
3. **symlink 过渡（临时补丁）**：0.13.0 首次激活曾因「就近单链 node_modules」缺陷导致 `@deepseek-ai/*` 解析失败，现场用**部署包内 3 个绝对路径 symlink**（把远层 `@deepseek-ai/*` 额外链进近层）应急恢复。`6d5da59` 的 `collectNodeModules` 合并式修复属稳定平面（reloader），**运行中 shell 需重启一次才生效**；且临时 symlink 补丁在 `pnpm install` 重装后会消失。**迭代规划**：下次重启加载新 shell 后，移除部署包内的临时 symlink 补丁。
4. **旧 ESM 模块图累积**：每次热换旧模块图留在进程模块表，不可回收。开发期已知可接受开销；长期高频 reload 需监控 RSS 并适时重启。
5. **改 shell/auth/reloader 需重启**：三者是稳定平面（shell 静态缓存、不参与热换），改 `auth.ts` 后 shell 自身两个路由仍走启动时缓存的旧逻辑直到重启；core 侧随版本目录立即换新。
6. **依赖不热换**：`node_modules`（ws/qrcode/@deepseek-ai/*）不随热换更新，升级依赖仍需重启。
7. **Phase A 残留细节**：`lsp.ts` 的 `pullDiagnostics` 自链式重试定时器句柄未登记（靠 `state.dead` 守卫空转自停）、mux 重连退避定时器最长残留 ~30s——均无害但未纳入 effect 清理；后续可在收紧时一并纳入。

### 9.2 迭代 roadmap

- **短中期**：
  - 移除部署包临时 symlink 补丁（重启加载新 shell 后）。
  - 部署脚本统一「先删后写」强制换 inode，根除硬链接混装。
  - 补一条「apply → dispose → 再 apply 不抛 duplicate route」的集成测试（当前 smoke mock 的 `effect`/`register` 为空实现，卸载路径无端到端覆盖）。
  - 把 Phase A 残留的裸定时器（pullDiagnostics 重试链、mux 退避）纳入 effect 清理，清零「卸载后仍泄漏」清单。
- **长期**：
  - 评估官方 HMR 演进，若其提供可注入事务/回滚的稳定接口，再考虑是否替换自举实现。
  - 内存治理：长期运行 reload 计数超阈值时，给出「建议重启」提示或自动调度重启窗口。
  - 依赖热换（可选）：探索把 `node_modules` 也纳入版本化暂存，但需先解决符号链接与 pnpm 布局的完整等价性（成本高，非刚需）。
- **触发再评估的条件**：官方 HMR 出现可用稳定接口；bridge 业务模块数量增长导致 copy+import 超过可接受时长；出现因硬链接混装/半写触发的生产事故。
